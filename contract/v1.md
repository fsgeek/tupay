# Service contract v1: a 3-node lease service with fencing tokens

Version 1, fixed 2026-10-20. Never edited in place. A later version is a new file; retired clause ids are never reused.

## Terms
- **Key.** One protected key. V1 has exactly one.
- **Lease nodes.** Three processes that together act as the **grantor**. How they agree is the implementation's business; the contract constrains only what the grantor does.
- **Storage.** The service that holds the key's value and the **fence ledger**: the highest token it has accepted for the key. Storage may be replicated internally; the contract treats it as one service.
- **Client.** A process that requests a grant and, while it believes it holds one, writes to storage.
- **Grant.** The grantor's reply to a request: a **token** (an integer) and a **lifetime** (a duration after which the holder must stop assuming the grant). A client holding an unexpired grant is a **holder**.
- **Write.** A client's request to storage carrying a value and a token. Storage either **accepts** or **rejects** it.
- **Ack.** The grantor's or storage's reply that reaches the client. "Told a write succeeded" means the client received an ack of acceptance.

## Clauses
- **C1.1** Each grant carries a token strictly greater than every token previously granted for the key.
- **C1.2** Storage accepts a write only if its token is at least the highest token storage has accepted for the key, and on acceptance records that token as the new highest.
- **C1.3** A client is told a write succeeded only after storage accepted it.
- **C1.4** (liveness) If a majority of lease nodes and storage stay up and connected to each other and to some requester for long enough, that requester eventually obtains a grant.

C1.1 to C1.3 are safety: they must hold in every execution the failure model admits. C1.4 is liveness: it is conditional on the environment behaving as stated.

## Observable events
These are the only events a test on either side may rely on. Each is recorded by the process that produces it, with that process's own sequence number. There is no cross-process clock.
- `Request(client, key)`
- `Grant(client, key, token, lifetime, grantor_term)` where `grantor_term` identifies which grantor incarnation issued it
- `WriteAttempt(client, key, token, value)`
- `WriteAccept(key, token, highest_before)` and `WriteReject(key, token, highest_before)` recorded by storage
- `WriteAck(client, key, token, outcome)` recorded by the client on receipt

## Out of scope in v1
Reads are not fenced (X1 will add this). There is one key. Tokens are not delegated (X3 will add this). Storage's ledger does not roll back; that is a later hold-out cell, not a v1 fault.
