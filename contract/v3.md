# Service contract v3: the grantor's membership changes

**DRAFT 3, not registered.** Drafted 2026-10-23 by the fifth steward for change experiment X3; drafts 2 and 3 after two input reviews (`experiments/X3/input-review/`; dispositions in the log). Nothing here is an input until X3's pre-registration commits it.

Version 3. v2 (`contract/v2.md`) and v1 are unchanged and their clause ids keep their meaning. v3 is **additive**: it adds a locus (configuration), terms, six clauses and observable events, and makes precise, for v3, terms that v1 and v2 left open ("made precise"). No earlier clause is retired. This file is self-contained: everything a reader needs from v1 and v2 is restated below, verbatim where marked.

## Terms (v1 and v2, restated verbatim)
- **Key:** one protected key. **Lease nodes:** processes that together act as the grantor. **Storage:** the service holding the key's value and the fence ledger (the highest token it has accepted for the key). **Client:** a process that requests a grant and, while it believes it holds one, writes to and reads from storage.
- **Grant:** the grantor's reply to a request, a token (an integer) and a lifetime; a client holding an unexpired grant is a holder.
- **Write:** a client's request to storage carrying a value and a token; storage accepts or rejects it. **Ack:** the reply that reaches the client; "told a write succeeded" means the client received an ack of acceptance.
- **Read:** a client's request to storage to return the key's current value, carrying a token. Storage either serves it, returning the value it currently holds, or rejects it. A client "is given a value" when it receives an ack of a served read carrying that value.

## Terms made precise for v3
- **Storage** is one process with one fence ledger and one stored value. (F1.1's "storage replica" means this process.)
- **Initial state.** Before any write the ledger is 0 and the stored value is absent (`null`). Tokens are positive integers, so every token exceeds the initial ledger.
- **Integers do not wrap.** Tokens, terms and epochs are unbounded integers. An implementation whose representation would overflow must record a failure and issue nothing, never a wrapped value.
- **Lifetime.** Every grant has the same lifetime `L`, a positive length of run time fixed by the deployment. Expiry is the grantor's concern, measured on the deciding node's own clock (`failure-model/v3.md`, F3.2). A client's belief about expiry decides nothing the contract checks: clients write and read when the workload tells them to.
- **Grantor term** (`grantor_term`): a positive integer identifying one leadership period of the grantor; no two leadership periods share a term. It is carried with the token on every write and read, and recorded on those events (below).
- **Outcomes.** A write's outcome is `accepted` or `rejected`; a read's is `served` or `rejected`; a reconfiguration's is `committed` or `refused`.

## Terms (new in v3)
- **Configuration:** a non-empty set of lease nodes, identified by a **configuration epoch** (a non-negative integer). The **initial configuration** has epoch 0 and is fixed by the deployment. Lease nodes outside every configuration may exist, up and connected, and may later be added.
- **Reconfiguration request:** a message from an operator to one lease node (the **receiver**), carrying a request id chosen by the operator and a set of process names (which may be empty, or name processes that are not lease nodes; such a request is refused as `invalid`). It obeys the link rules of the failure model like any message.
- **Committed:** a configuration is committed when the grantor has decided, irrevocably, that it supersedes its predecessor. A node's **current configuration** is the committed configuration with the highest epoch that the node has recorded. A change from epoch e to e+1 may pass through internal states (such as Raft's joint configuration); they are not configurations here and have no epoch.
- **Vote:** a lease node's agreement to a proposal, recorded by the node itself (`Vote`). A proposal is a grant under a stated configuration, or a configuration for a stated epoch.
- **Incarnation:** a lease node's incarnation starts at 0 and increases by one at each amnesic restart (failure model, F3.3). An ordinary restart keeps the incarnation.
- **Eligible vote.** A vote counts toward a majority only if, when it was sent, its sender was a member of the configuration it votes under, and its incarnation was either 0 or had been re-added: a configuration listing the node was committed from a request sent after the amnesia that began that incarnation.
- **Majority of a configuration:** eligible votes from more than half of all its members. The denominator is the whole membership; an ineligible member is not removed from it, or two majorities might not intersect.
- **Pending.** A reconfiguration request is pending at its receiver from when the receiver records it (`ReconfigRequest`) until the receiver records its commit, its refusal, or a commit of any higher epoch, or the receiver restarts amnesic. It is pending nowhere else.

## Clauses (v1 and v2, restated verbatim)
- **C1.1** Each grant carries a token strictly greater than every token previously granted for the key.
- **C1.2** Storage accepts a write only if its token is at least the highest token storage has accepted for the key, and on acceptance records that token as the new highest.
- **C1.3** A client is told a write succeeded only after storage accepted it.
- **C1.4** (liveness) If a majority of lease nodes and storage stay up and connected to each other and to some requester for long enough, that requester eventually obtains a grant.
- **C2.1** Storage serves a read only if its token is at least the highest token storage has accepted for the key. Serving a read does not change the highest accepted token.
- **C2.2** A client is given a value only after storage served the read that returned it, and the value given is the value storage held when it served the read.

### How v1 and v2 read under v3 (made precise; no clause changes)
- **Storage decides deterministically.** Storage accepts a write **if and only if** its token is at least the ledger, and on acceptance stores the write's value (an equal token replaces the value); it serves a read **if and only if** its token is at least the ledger, returning the stored value. C1.2 and C2.1 permit this rule; C3.5 needs a rule, and v3 fixes this one.
- **C1.1 across configurations.** "Every token previously granted" means under every configuration.
- **Fencing.** A newer grant does not by itself stop an older holder: storage rejects the older holder only once a write or read with a newer token has been accepted or served. This is v1's meaning; F1.3 is the case it exists for.
- **C1.4 under v3.** "A majority of lease nodes" means a majority (eligible votes, as above) of the configuration with the highest committed epoch. The premise holds only after the last fault of the run (failure model, "After the last fault") and only while no reconfiguration request is pending at any member of that majority.

## Clauses (new in v3)
- **C3.1** Epoch e+1 is committed only after epoch e, and at most one configuration is committed for any epoch.
- **C3.2** A grant is issued under exactly one configuration, the deciding node's current configuration, records that configuration's epoch, is issued only after a majority of that configuration voted for it, and carries a token greater than the highest token sealed by that configuration's commit (`ConfigCommitted`, `highest_token`; 0 for epoch 0).
- **C3.3** Configuration epoch e+1 is committed only after a majority of configuration e and a majority of configuration e+1 voted for it, and its commit seals a `highest_token` at least as high as every token any of the counted voters of configuration e reported in those votes. An operator is told a reconfiguration succeeded only for the request whose id the commit names, and only after that commit.
- **C3.4** (liveness) If, after the last fault, a request is pending at its receiver, and the receiver, a majority of the configuration with the highest committed epoch and a majority of the requested set stay up and connected to each other for long enough, the request is eventually committed or refused at the receiver for a reason other than `unavailable`; and if the operator also stays connected to the receiver, it is eventually told which (`ReconfigAck`). Refusal reasons: `superseded` (a higher epoch was committed while it was pending), `invalid` (its set is empty or names a process that is not a lease node), `busy` (a request that reached the same receiver earlier is still pending there; the earlier one is never refused as `busy` on account of the later), `unavailable` (the receiver gave up; allowed at any time, and not progress under this clause).
- **C3.5** (reconstructibility) Every decision the service records is a function of the inputs recorded with it: in any two runs of the same artifact, two decisions of the same kind whose recorded inputs are equal have equal outcomes. A decision that consulted anything it did not record (a clock read, a random draw, a scheduling accident, the iteration order of an unordered collection) violates C3.5 when that input changes the outcome.
- **C3.6** (votes) A lease node never votes for a grant under epoch e after it has voted for a configuration of a higher epoch, and never votes for two different configurations for the same epoch. In a vote for a configuration it reports the highest token it has voted for or learned of. These promises hold across ordinary restarts (they are durable); an amnesic incarnation has forgotten them, which is why its votes are not eligible until it is re-added.

C3.1, C3.2, C3.3, C3.5 and C3.6 are safety clauses; C3.4 is liveness. C3.2, C3.3 and C3.6 together are what carry C1.1 across a configuration change: any majority of e that voted for a grant shares a voter with the majority of e that voted for e+1, and C3.6 makes that voter's grant vote come first, so the commit's sealed token covers it.

## Observable events (v1 and v2, restated verbatim)
`Request(client, key)`; `Grant(client, key, token, lifetime, grantor_term)`; `WriteAttempt(client, key, token, value)`; `WriteAccept(key, token, highest_before)` and `WriteReject(key, token, highest_before)` recorded by storage; `WriteAck(client, key, token, outcome)` recorded by the client; `ReadAttempt(client, key, token)`; `ReadAccept(key, token, highest_before, value)` and `ReadReject(key, token, highest_before)` recorded by storage; `ReadAck(client, key, token, outcome, value)` recorded by the client, `value` present only when `outcome` is `served`. Each is recorded by the process that produces it, with that process's own sequence number; there is no cross-process clock.

## Observable events (new or extended in v3)
- The eight write and read events above also carry `grantor_term` (the term carried with the token).
- `Grant` gains `config_epoch`.
- `Vote(voter, incarnation, proposal, config_epoch, reported_token)` recorded by the voter when it votes. `proposal` is the whole proposal: for a grant, client, token, lifetime and `config_epoch`; for a configuration, epoch, members and request id. `reported_token` is present on configuration votes (C3.6).
- `Agreed(decider, voter, voter_incarnation, proposal, config_epoch, reported_token)` recorded only by the deciding node, once per voter, when it receives that voter's vote (its own included).
- `ConfigCommitted(node, epoch, members, request_id, highest_token, highest_term, decided)` recorded by every lease node when it learns that a configuration is committed; `decided` is true only at the node that decided the commit, exactly once per epoch above 0. Every member of the initial configuration records it for epoch 0 when it first starts, with `request_id` null, `highest_token` 0 and `decided` false.
- `ReconfigSend(operator, request_id, to, members)` recorded by the operator when it sends; `ReconfigRequest(operator, request_id, members)` recorded by the receiver.
- `ReconfigRefused(node, request_id, reason, epoch)` recorded by the receiver when it refuses; `epoch` is the superseding epoch for `superseded` and null otherwise.
- `ReconfigAck(operator, request_id, outcome, epoch)` recorded by the operator on receipt; the reply carries the identity of the receiver's commit or refusal record, which the ack names in its causes.
- **Decision inputs (C3.5).** Every decision record carries the inputs it consulted, as named values, in the format of `observe/schema.md`, v5 addendum.

## Out of scope in v3
One key. Quorums are majorities of one configuration, or, for a configuration commit (C3.3), majorities of the old and the new one; no other quorum system. How clients find the current configuration is the artifact's choice. No delegated tokens; no ledger rollback; no cryptography.
