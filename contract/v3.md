# Service contract v3: the grantor's membership changes

**DRAFT, not registered.** Drafted 2026-10-23 by the fifth steward for change experiment X3. Nothing here is an input until X3's pre-registration commits it; until then it may change, and every change is logged.

Version 3. v2 (`contract/v2.md`) and v1 are unchanged and their clause ids keep their meaning. v3 is **additive**: it adds a locus (configuration), terms, four clauses and observable events. No earlier clause is retired. This file is self-contained: everything a reader needs from v1 and v2 is restated below, verbatim where marked.

## Terms (v1 and v2, restated verbatim)
- **Key:** one protected key. **Lease nodes:** processes that together act as the grantor. **Storage:** the service holding the key's value and the fence ledger (the highest token it has accepted for the key). **Client:** a process that requests a grant and, while it believes it holds one, writes to and reads from storage.
- **Grant:** the grantor's reply to a request, a token (an integer) and a lifetime; a client holding an unexpired grant is a holder.
- **Write:** a client's request to storage carrying a value and a token; storage accepts or rejects it. **Ack:** the reply that reaches the client; "told a write succeeded" means the client received an ack of acceptance.
- **Read:** a client's request to storage to return the key's current value, carrying a token. Storage either serves it, returning the value it currently holds, or rejects it. A client "is given a value" when it receives an ack of a served read carrying that value.

## Terms (new in v3)
- **Configuration:** a non-empty set of lease nodes, identified by a **configuration epoch** (an integer). The initial configuration has epoch 0 and is fixed by the deployment. Only members of a configuration may take part in granting under it.
- **Reconfiguration request:** an operator's request, delivered to any lease node, naming a new set of lease nodes. Nodes that are not members of any configuration may exist, up and connected, and may later be added.
- **Committed:** a configuration is committed when the grantor has decided, irrevocably, that it supersedes its predecessor. How it decides is the artifact's choice (the implementation may use its Raft library's membership change); what it decides is observable (below).
- **Majority of a configuration:** more than half of its members.

## Clauses (v1 and v2, restated verbatim)
- **C1.1** Each grant carries a token strictly greater than every token previously granted for the key.
- **C1.2** Storage accepts a write only if its token is at least the highest token storage has accepted for the key, and on acceptance records that token as the new highest.
- **C1.3** A client is told a write succeeded only after storage accepted it.
- **C1.4** (liveness) If a majority of lease nodes and storage stay up and connected to each other and to some requester for long enough, that requester eventually obtains a grant.
- **C2.1** Storage serves a read only if its token is at least the highest token storage has accepted for the key. Serving a read does not change the highest accepted token.
- **C2.2** A client is given a value only after storage served the read that returned it, and the value given is the value storage held when it served the read.

C1.1 holds across configurations: a grant issued under any configuration carries a token greater than every token granted under every earlier one. v3 does not restate this as a new clause because C1.1 already says it.

Under v3, "a majority of lease nodes" in C1.4 means a majority of the configuration committed most recently before the premise begins to hold, and C1.4's premise is held only while no reconfiguration request is pending.

## Clauses (new in v3)
- **C3.1** Committed configurations have strictly increasing epochs, and at most one configuration is committed for any epoch.
- **C3.2** A grant is issued under exactly one configuration, records that configuration's epoch, and is issued only after a majority of that configuration agreed to it. No member counted in that majority had, when it agreed, recorded `ConfigCommitted` for a higher epoch. (With no cross-process clock, "a stale configuration may not grant" is stated in terms of what the agreeing members had learned; that the commit of a new configuration reaches enough of the old one to make this hold is the artifact's work.)
- **C3.3** An operator is told a reconfiguration succeeded only after the configuration it requested was committed.
- **C3.4** (liveness) If, after a reconfiguration request, a majority of the current configuration and a majority of the requested configuration stay up and connected to each other for long enough, the requested configuration is eventually committed, or the operator is told the request was refused because a different reconfiguration was committed first.
- **C3.5** (reconstructibility) Every decision the service records (a grant, a storage accept or reject, a configuration commit) can be re-derived from the inputs recorded before it in the trace: the recorded inputs determine the decision's outcome. A decision whose outcome depends on anything not recorded (a clock read, a random draw, a scheduling accident) violates C3.5 unless that input is itself recorded where the decision consults it.

C3.1, C3.2, C3.3 and C3.5 are safety clauses; C3.4 is liveness.

## Observable events (v1 and v2, restated verbatim)
`Request(client, key)`; `Grant(client, key, token, lifetime, grantor_term)`; `WriteAttempt(client, key, token, value)`; `WriteAccept(key, token, highest_before)` and `WriteReject(key, token, highest_before)` recorded by storage; `WriteAck(client, key, token, outcome)` recorded by the client; `ReadAttempt(client, key, token)`; `ReadAccept(key, token, highest_before, value)` and `ReadReject(key, token, highest_before)` recorded by storage; `ReadAck(client, key, token, outcome, value)` recorded by the client, `value` present only when `outcome` is `served`. Each is recorded by the process that produces it, with that process's own sequence number; there is no cross-process clock.

## Observable events (new in v3)
- `Grant` gains a field: `Grant(client, key, token, lifetime, grantor_term, config_epoch)`.
- `ReconfigRequest(operator, node, members)` recorded by the node that receives it.
- `ConfigCommitted(node, epoch, members)` recorded by every lease node when it learns that a configuration is committed.
- `ReconfigAck(operator, members, outcome)` recorded by the operator on receipt; `outcome` is `committed` or `refused`.
- `Agreed(node, decision, config_epoch, highest_committed_epoch)` recorded by a lease node when it agrees to a grant or a configuration commit under the configuration with that epoch, or by the deciding node when it receives that agreement (the record says which); `highest_committed_epoch` is the highest epoch for which the agreeing node had recorded `ConfigCommitted` when it agreed, as the agreement reports it; `decision` names the grant (by token) or the configuration (by epoch). A grant's or commit's decision inputs name the `Agreed` records it counted.
- **Decision inputs (C3.5).** Every recorded decision lists the inputs it consulted, each either an earlier record (by process and sequence number) or a value recorded with the decision itself (a clock reading, a random draw). The format is `observe/schema.md`, v5 addendum.

## Out of scope in v3
One key. Majority quorums only (no other quorum system). How clients discover the current configuration's members is the artifact's choice; C1.4 and C3.4 promise progress, not a discovery mechanism. No delegated tokens; no ledger rollback; no cryptography.
