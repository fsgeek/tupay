# Service contract v3: the grantor's membership changes

**DRAFT 2, not registered.** Drafted 2026-10-23 by the fifth steward for change experiment X3; draft 2 after an input review (`experiments/X3/input-review/`). Nothing here is an input until X3's pre-registration commits it.

Version 3. v2 (`contract/v2.md`) and v1 are unchanged and their clause ids keep their meaning. v3 is **additive**: it adds a locus (configuration), terms, five clauses and observable events, and it makes precise, for v3, terms that v1 and v2 left open (marked "made precise"). No earlier clause is retired. This file is self-contained: everything a reader needs from v1 and v2 is restated below, verbatim where marked.

## Terms (v1 and v2, restated verbatim)
- **Key:** one protected key. **Lease nodes:** processes that together act as the grantor. **Storage:** the service holding the key's value and the fence ledger (the highest token it has accepted for the key). **Client:** a process that requests a grant and, while it believes it holds one, writes to and reads from storage.
- **Grant:** the grantor's reply to a request, a token (an integer) and a lifetime; a client holding an unexpired grant is a holder.
- **Write:** a client's request to storage carrying a value and a token; storage accepts or rejects it. **Ack:** the reply that reaches the client; "told a write succeeded" means the client received an ack of acceptance.
- **Read:** a client's request to storage to return the key's current value, carrying a token. Storage either serves it, returning the value it currently holds, or rejects it. A client "is given a value" when it receives an ack of a served read carrying that value.

## Terms made precise for v3
- **Storage** is one process with one fence ledger and one stored value. (F1.1's "storage replica" means this process.)
- **Initial state.** Before any write the ledger is 0 and the stored value is absent (`null`). Tokens are positive integers, so every token exceeds the initial ledger.
- **Lifetime.** Every grant has the same lifetime `L`, a positive length of run time fixed by the deployment. Each process measures elapsed time on its own clock (`failure-model/v3.md`, F3.2).
- **Grantor term** (`grantor_term`): a positive integer identifying one leadership period of the grantor; no two leadership periods share a term. It is carried with the token on every write and read.
- **Outcomes.** A write's outcome is `accepted` or `rejected`; a read's is `served` or `rejected`; a reconfiguration's is `committed` or `refused`.

## Terms (new in v3)
- **Configuration:** a non-empty set of lease nodes, identified by a **configuration epoch** (a non-negative integer). The **initial configuration** has epoch 0 and is fixed by the deployment. Lease nodes outside every configuration may exist, up and connected, and may later be added.
- **Reconfiguration request:** a message from an operator to one lease node (the **receiver**), carrying a request id chosen by the operator and a set of lease nodes. It obeys the link rules of the failure model like any message.
- **Committed:** a configuration is committed when the grantor has decided, irrevocably, that it supersedes its predecessor. The **current configuration** is the committed configuration with the highest epoch. A change from epoch e to epoch e+1 may pass through internal states (such as Raft's joint configuration); they are not configurations in this contract and have no epoch.
- **Majority of a configuration:** more than half of its members, not counting **amnesic** members (failure model, F3.3) that no committed configuration has re-added since their amnesia.
- **Pending.** A reconfiguration request is pending at a lease node from when the node records it (`ReconfigRequest`, or by learning of it from another node) until the node records its commit or its refusal.

## Clauses (v1 and v2, restated verbatim)
- **C1.1** Each grant carries a token strictly greater than every token previously granted for the key.
- **C1.2** Storage accepts a write only if its token is at least the highest token storage has accepted for the key, and on acceptance records that token as the new highest.
- **C1.3** A client is told a write succeeded only after storage accepted it.
- **C1.4** (liveness) If a majority of lease nodes and storage stay up and connected to each other and to some requester for long enough, that requester eventually obtains a grant.
- **C2.1** Storage serves a read only if its token is at least the highest token storage has accepted for the key. Serving a read does not change the highest accepted token.
- **C2.2** A client is given a value only after storage served the read that returned it, and the value given is the value storage held when it served the read.

### How v1 and v2 read under v3 (made precise; no clause changes)
- **Storage decides deterministically.** Under v3, storage accepts a write **if and only if** its token is at least the ledger, and on acceptance stores the write's value (an equal token replaces the value); it serves a read **if and only if** its token is at least the ledger, returning the stored value. C1.2 and C2.1 permit this rule; C3.5 requires a rule, and v3 fixes this one so that storage is the same in every artifact.
- **C1.1 across configurations.** "Every token previously granted" means under every configuration.
- **Fencing.** A newer grant does not by itself stop an older holder: storage rejects the older holder only once a write or read with a newer token has been accepted or served. This is v1's meaning, and F1.3 is the case it exists for.
- **C1.4 under v3.** "A majority of lease nodes" means a majority of the current configuration. The premise holds only while no reconfiguration request is pending at any member of that majority, and only after the last fault of the run (failure model, "After the last fault").

## Clauses (new in v3)
- **C3.1** Committed configurations have strictly increasing epochs: epoch e+1 is committed only after epoch e, and at most one configuration is committed for any epoch.
- **C3.2** A grant is issued under exactly one configuration, the current one at the deciding node, records that configuration's epoch, and is issued only after a majority of that configuration agreed to it. No member counted in that majority had, at any point in the run before it agreed (including before a restart, with or without its durable state), recorded `ConfigCommitted` for a higher epoch. (A node that forgot a newer configuration is still bound by it: the trace remembers what the node does not.)
- **C3.3** Configuration epoch e+1 is committed only after a majority of configuration e and a majority of configuration e+1 agreed to it. An operator is told a reconfiguration succeeded only after the configuration it requested was committed.
- **C3.4** (liveness) If, from when a reconfiguration request reaches its receiver, the receiver, a majority of the current configuration and a majority of the requested set stay up and connected to each other, after the last fault, for long enough, then the request is eventually committed or refused at the receiver; and if the operator also stays connected to the receiver, it is eventually told which (`ReconfigAck`). A request may be refused only for a reason recorded with the refusal: another configuration was committed while it was pending (`superseded`), its set is empty or names a process that is not a lease node (`invalid`), or another request that reached the same receiver earlier was still pending there (`busy`; the earlier request is not refusable as `busy` on account of the later one).
- **C3.5** (reconstructibility) Every decision the service records is a function of the inputs recorded with it: in any two runs of the same artifact, two decisions of the same kind whose recorded inputs are equal have equal outcomes. A decision that consulted anything it did not record (a clock read, a random draw, a scheduling accident, the iteration order of an unordered collection) violates C3.5 when that input changes the outcome.

C3.1, C3.2, C3.3 and C3.5 are safety clauses; C3.4 is liveness.

## Observable events (v1 and v2, restated verbatim)
`Request(client, key)`; `Grant(client, key, token, lifetime, grantor_term)`; `WriteAttempt(client, key, token, value)`; `WriteAccept(key, token, highest_before)` and `WriteReject(key, token, highest_before)` recorded by storage; `WriteAck(client, key, token, outcome)` recorded by the client; `ReadAttempt(client, key, token)`; `ReadAccept(key, token, highest_before, value)` and `ReadReject(key, token, highest_before)` recorded by storage; `ReadAck(client, key, token, outcome, value)` recorded by the client, `value` present only when `outcome` is `served`. Each is recorded by the process that produces it, with that process's own sequence number; there is no cross-process clock.

## Observable events (new in v3)
- `Grant` gains `config_epoch`: `Grant(client, key, token, lifetime, grantor_term, config_epoch)`.
- `ConfigCommitted(node, epoch, members, request_id)` recorded by every lease node when it learns that a configuration is committed (`request_id` null for epoch 0). Every member of the initial configuration records `ConfigCommitted` for epoch 0 when it first starts.
- `ReconfigSend(operator, request_id, to, members)` recorded by the operator when it sends a request; `ReconfigRequest(operator, request_id, members)` recorded by the receiver.
- `ReconfigRefused(node, request_id, reason, epoch)` recorded by the node that decides a refusal; `epoch` is the superseding configuration's for `superseded`.
- `ReconfigAck(operator, request_id, outcome, epoch)` recorded by the operator on receipt.
- `Agreed(decider, voter, proposal, config_epoch, voter_highest_epoch)` recorded **only by the deciding node**, once per voter, when it receives that voter's agreement (its own included). `proposal` is the whole proposal: for a grant, client, token, lifetime and `config_epoch`; for a configuration, epoch, members and request id. `voter_highest_epoch` is the highest epoch for which the voter reports having recorded `ConfigCommitted`.
- **Decision inputs (C3.5).** Every decision record carries the inputs it consulted, as named values, in the format of `observe/schema.md`, v5 addendum.

## Out of scope in v3
One key. Quorums are majorities of one configuration, or, for a configuration commit (C3.3), majorities of the old and the new one; no other quorum system. How clients find the current configuration is the artifact's choice. No delegated tokens; no ledger rollback; no cryptography.
