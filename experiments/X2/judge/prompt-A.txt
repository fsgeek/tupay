# Service contract v2: reads are fenced too

Version 2, fixed 2026-10-21. v1 (`contract/v1.md`) is unchanged and its clause ids C1.1 to C1.4 keep their meaning. v2 is **additive**: it adds terms, two clauses and four observable events. No v1 clause is retired. This is change experiment X1's input.

## Terms (in addition to v1's)
- **Read.** A client's request to storage to return the key's current value, carrying a token. Storage either **serves** it, returning the value it currently holds, or **rejects** it.
- **Given a value.** A client "is given a value" when it receives an ack of a served read carrying that value.

## Clauses (C1.1 to C1.4 as in v1, plus)
- **C2.1** Storage serves a read only if its token is at least the highest token storage has accepted for the key. Serving a read does not change the highest accepted token.
- **C2.2** A client is given a value only after storage served the read that returned it, and the value given is the value storage held when it served the read.

C2.1 and C2.2 are safety clauses. C1.4 (liveness) is unchanged and says nothing about reads.

## Observable events (in addition to v1's)
- `ReadAttempt(client, key, token)`
- `ReadAccept(key, token, highest_before, value)` and `ReadReject(key, token, highest_before)` recorded by storage; `highest_before` is the fence ledger at the decision, as for writes
- `ReadAck(client, key, token, outcome, value)` recorded by the client on receipt; `value` is present only when `outcome` is `served`

## Out of scope in v2
As in v1: one key; no delegated tokens; no ledger rollback. A read served under a token that is later superseded is not a violation; the fence decides at the moment of the read, as it does for writes.

## Amendment 2026-10-21: v1 restated for readers who have no v1 (additive; no clause changes)
This section was added after the X1 regenerate arm started, when its implementation author reported that the C1 clauses were "missing" from its inputs (its interpretation 1): v2 referred to v1 by id without restating it, and the regenerate arm is deliberately not given v1. Nothing above changes; the ids and wording below are v1's, verbatim.

**Terms (v1).** Key: one protected key. Lease nodes: three processes that together act as the grantor. Storage: the service holding the key's value and the fence ledger (the highest token it has accepted for the key). Client: a process that requests a grant and, while it believes it holds one, writes to storage. Grant: the grantor's reply to a request, a token (an integer) and a lifetime; a client holding an unexpired grant is a holder. Write: a client's request to storage carrying a value and a token; storage accepts or rejects it. Ack: the reply that reaches the client; "told a write succeeded" means the client received an ack of acceptance.

**Clauses (v1).**
- **C1.1** Each grant carries a token strictly greater than every token previously granted for the key.
- **C1.2** Storage accepts a write only if its token is at least the highest token storage has accepted for the key, and on acceptance records that token as the new highest.
- **C1.3** A client is told a write succeeded only after storage accepted it.
- **C1.4** (liveness) If a majority of lease nodes and storage stay up and connected to each other and to some requester for long enough, that requester eventually obtains a grant.

**Observable events (v1).** `Request(client, key)`; `Grant(client, key, token, lifetime, grantor_term)`; `WriteAttempt(client, key, token, value)`; `WriteAccept(key, token, highest_before)` and `WriteReject(key, token, highest_before)` recorded by storage; `WriteAck(client, key, token, outcome)` recorded by the client. Each is recorded by the process that produces it, with that process's own sequence number; there is no cross-process clock.

# Failure model v2

Version 2, fixed 2026-10-21 for change experiment X2. v1 (`failure-model/v1.md`) is unchanged and its cell ids F1.1 to F1.3 keep their meaning. v2 is **additive**: it adds a vocabulary of links, two cells and a definition of "connected". No v1 cell is retired. This file is self-contained: everything a reader needs from v1 is restated below, verbatim where marked.

A failure model is an **environment** (what the world can do) applied to **authority loci** (where a grant, a token, or a decision lives). A test cell is one environmental fault applied during one transition. The loci are named so that later changes are visibly additions.

## Authority loci (unchanged from v1)
- **Holder:** the client that believes it has an unexpired grant.
- **Grantor:** the lease leader of the moment, identified by `grantor_term`.
- **Fence ledger:** storage's highest accepted token for the key.

v2 adds no locus. X2 is registered as a **parameter change**: the environment can do more, and nothing new holds authority.

## Links (new in v2)
Between every ordered pair of distinct processes (p, q) there is a **link p→q**, which is either up or down. A message p sends to q is delivered (possibly reordered or duplicated, never corrupted) only if p→q is up when it is sent; a message sent while p→q is down is lost, not delayed. A link's state changes only by a fault step and by a heal. A message's fate is fixed when it is sent: a message sent while p→q is up is delivered (it may arrive late, reordered, after p→q has gone down); a message sent while p→q is down is never delivered, even if the link comes back up.

**Connected.** Two processes p and q are *connected* while both p→q and q→p are up. A set of processes is *connected to each other* while every two of its members are connected. Connection is direct: p and q are not connected because both are connected to some r. This is the meaning of "connected" in C1.4 (`contract/v2.md`) under failure model v2. Under v1 every fault left connectivity transitive, so v1 never had to say it.

## Cells
v1's cells, restated verbatim:
- **F1.1 Crash-stop.** Any lease node, client, or storage replica stops without warning. It may later restart with whatever it had durably recorded and nothing else. A restarted client has no grant.
- **F1.2 Complete partition.** The processes are split into two sides. No message crosses between sides until the partition heals. Any bipartition is allowed, including one that isolates the current grantor from the other lease nodes while leaving it connected to a holder, or that isolates a holder from the grantor while leaving it connected to storage. Partitions heal; messages sent across the cut during the partition are lost, not delayed.
- **F1.3 Holder pause.** A client holding a grant is paused for longer than the grant's lifetime, then resumes and continues as if no time had passed. This is the case fencing tokens exist for.

New in v2:
- **F2.1 Partial partition.** Any set of links goes down in both directions, whether or not the result is a bipartition. Connectivity may become non-transitive: p and q connected, q and r connected, p and r not. In the vocabulary of links, F1.2 is the special case in which the down links are exactly those between two sides.
- **F2.2 Simplex link failure.** Any set of links goes down in one direction only: p→q down while q→p stays up. A process may then hear from a peer it cannot answer, or be heard by a peer it cannot hear.
- **Heal.** A heal restores every link, whichever cells took them down.

Faults compose: a schedule may apply several cells in one run, and link failures accumulate until a heal. Messages on an up link may be reordered and duplicated but not corrupted.

## Not in v2
Delegated tokens (X3). Byzantine behaviour. Ledger rollback or storage restored from backup. Clock skew beyond what F1.3 produces. Links that delay rather than lose. Link failures that change while a message is in flight (a message's fate is fixed when it is sent).

## What counts as an unknown category
A violation of C1.1, C1.2, C1.3, C2.1 or C2.2, or of C1.4 in a run whose fault schedule satisfies C1.4's premise, observed in a run whose schedule contains only F1.1 to F1.3, F2.1 and F2.2, and which no cell explains, is an unknown category. It is reported as **unexplained** until a judge discriminates. It is not assumed to be the implementation's fault.

## Changelog
- v2 (2026-10-21): links; "connected" defined; F2.1, F2.2; heal restores every link. Reason: the parameter change held out in v1's "Not in v1".

# Fault schedule format v2.2 (shared interface)

v2.2 fixed 2026-10-21 after X1 (one clarification, listed in the changelog). v2.1 fixed 2026-10-21 (two clarifications). v2 fixed 2026-10-20 by the steward, after M1's cross-run. v1 is kept as `schedule-format-v1.md`; nothing in it is removed. v2 adds the rules that v1 left open and that the judge named (M1 result, D2 and D3). Every schedule compiler derives from this file; a compiler that implements v1 is stale under v2.

## Shape (unchanged from v1)
```yaml
schedule: <name>                 # unique; used as the run id
derives: [F1.2, C1.2]            # cells and clauses this schedule exercises
processes:
  lease: [n1, n2, n3]
  clients: [c1, c2]
  storage: [s]
steps:                           # applied in order; each waits for its trigger
  - at: <trigger>
    do: <action>
end: <trigger>                   # see "End of a run"
bound: {events: 200}             # safety bound for both sides
```

## Triggers
A trigger is `start` or an observable event from `contract/v1.md` with optional field filters:
```yaml
at: start
at: {event: Grant, client: c1}
at: {event: WriteAck, client: c2, outcome: accepted}
at: {event: WriteReject}
```

**Rule T1, arming (new in v2; settles D2).** Step 1's trigger is armed at the start of the run. Step *i*'s trigger (*i* > 1) is armed at the moment step *i*−1's action is taken. A trigger matches only events emitted **after** it was armed. An event emitted before the trigger was armed never satisfies it, however well it matches. `start` fires the moment it is armed. **(v2.1)** The events that step *i*−1's own action emits synchronously (its `Request`, `WriteAttempt` or `Fault`) count as emitted after step *i*'s trigger was armed, so a step may be triggered by the event its predecessor produced. Both authors read v2 this way; v2.1 says it.

**Rule T2, taking the action.** Once a step's trigger has fired, the action is taken at some later point. The model side explores every such point; the impl side samples one. The next step's trigger is not armed until the action is taken, so no two steps are ever pending at once.

**Rule T3, waiting workload.** A workload action (`request`, `write`) whose client is crashed or paused waits until the client is running. A `request` by a client that already has a request outstanding waits until that request is answered. A `write` by a client that holds no token waits until it holds one, except `token: stale`, which waits until the client has a superseded token.

## Actions (unchanged from v1 except as marked)
Workload:
```yaml
do: {request: c1}
do: {write: c1, value: v1}                # with the client's current token
do: {write: c1, value: v2, token: stale}  # with the client's most recent token that is lower than the highest token granted so far
```
Faults, one per cell:
```yaml
do: {cell: F1.1, crash: n2}
do: {cell: F1.1, restart: n2}
do: {cell: F1.2, partition: [[grantor, c1, s], [rest]]}
do: {cell: F1.2, heal: true}
do: {cell: F1.3, pause: c1}
do: {cell: F1.3, resume: c1}
```
A `pause` must outlast the grant's lifetime: the matching `resume` must be triggered by an event that can only happen after expiry (a later `Grant` to another client, or an ack of a write made under a later grant).

**Rule A1, aliases (new in v2; settles D3).** `grantor`, `holder` and `rest` are process selectors and may appear **wherever a process name may appear**: as the target of `crash`, `restart`, `pause`, `resume`, `request` and `write`, and as members of a partition side. `grantor` is the node that issued the most recent `Grant` event; `holder` is the client that received it; `rest` is every process not named on the other side of the same partition. Aliases are resolved at the moment the step's trigger fires. A schedule that uses `grantor` or `holder` before any `Grant` can have occurred is rejected by the compiler. **(v2.1)** A fourth selector, `non-grantor`, means a lease node other than `grantor` that is up at the moment the trigger fires. The model side explores every such node; the impl side picks the lowest-numbered one. It exists because leadership before the first `Grant` is not observable, so "crash a follower" can only be said after a grant. **(v2.2)** `restart: non-grantor` names the node that the most recent `crash: non-grantor` crashed, whether or not it is a non-grantor at the moment of the restart; a schedule with `restart: non-grantor` and no earlier `crash: non-grantor` is rejected. All four fresh-arm authors in X1 read v2.1 this way and flagged that the text did not say it.

**Rule A2, crash and restart.** `restart` of a process that is not crashed, `crash` of a process already crashed, `pause` of a paused client, `resume` of a running client, and `pause` of a lease node or storage are all rejected by the compiler.

## End of a run
**Rule E1 (new in v2).** `end:` is either an event trigger, armed when the last step's action is taken and matched by Rule T1, or the word `quiescent`. `quiescent` means: every step has been applied and no request, write or ack is in flight and no client is waiting for a grant, with crashed and paused processes not counted. On the model side `quiescent` is a state predicate; on the impl side it is a bounded wait for in-flight work, after which an unanswered request is reported through the liveness checker, not as `end` unreachable. The shared schedules use `quiescent` unless the end must be a specific event.

**Rule E2.** A clause violation witnessed before the end is a `FAIL` whether or not the end is reached. `UNEXPLAINED end unreachable` is reported only when no violation was witnessed.

## Rules carried from v1
- A schedule may not name an action the failure model does not contain; the compiler rejects it.
- Nondeterminism the schedule leaves open (message order within a side, delay between trigger and action) is explored by TLC and sampled by the impl. A pass on one side and a failure on the other is a divergence, not a bug on either side.
- **Schedules live in `testbed/schedules/<name>.yaml` and nowhere else.** Both runners resolve a name there. The authors' private schedule sets from M1 are kept under their own directories as history and are no longer run.

- v2.1 (2026-10-21): T1 clarified for a predecessor's own events; `non-grantor` selector. Reasons: M1 result, round 2 residues. Shared P10 rewritten to use it.
- v2 (2026-10-20): T1 arming, T2, T3, A1 aliases, A2, E1 `quiescent`, E2; schedules shared. Reasons: M1 result D2 and D3.

```yaml

do: {read: c1, token: stale}   # with its most recent token lower than the highest granted so far
```
Rule T3 applies to `read` as it does to `write`. Triggers may name the new events `ReadAttempt`, `ReadAccept`, `ReadReject` and `ReadAck` (with `outcome: served` or `rejected`). Changelog: v3 (2026-10-21): `read` action and the four read events. Reason: X1, contract v2.

## v4 addendum (2026-10-21, for failure model v2; additive)
Two fault actions are added, one per new cell. Everything above is unchanged; a compiler that implements v3 and not v4 is stale only for schedules that name F2.1 or F2.2.
```yaml
do: {cell: F2.1, cut: [[n1, n3], [grantor, c2]]}    # each listed link goes down in both directions
do: {cell: F2.2, drop: [[n2, grantor], [n3, grantor]]}  # messages from the first to the second are lost; the reverse direction is untouched
do: {cell: F2.1, heal: true}                          # restores every link (also {cell: F2.2, heal: true} and {cell: F1.2, heal: true})
```
**Rule L1, links.** Each entry of `cut` or `drop` is a pair of process names or selectors. `grantor`, `holder` and `non-grantor` are allowed and are resolved as Rule A1 says, at the moment the step's trigger fires; `rest` is not allowed in a link, since it is defined only against a partition side. A pair whose two ends resolve to the same process is ignored, so `[n1, grantor]` is safe whichever node is the grantor. Taking down a link that is already down is allowed and changes nothing. A selector names one process per pair; to reach both followers write the pairs out (`[[grantor, n1], [grantor, n2], [grantor, n3]]` reaches exactly the two that are not the grantor).

**Rule L2, accumulation.** Link failures from `cut`, `drop` and F1.2 `partition` accumulate. A `heal`, whatever cell it names, restores every link. There is no partial heal.

**Rule L3, the premise of C1.4.** Whether a run's schedule satisfies C1.4's premise is read with "connected" as `failure-model/v2.md` defines it: both directions of the direct link up. A schedule whose comment claims a requester "should eventually get a grant" must leave a majority of lease nodes, storage and that requester connected to each other for the rest of the run after its last fault. The premise is read **literally**: it names no grantor, so the majority need not include the grantor of the moment, and the requester need not be connected to it. If the premise holds, the requester must eventually obtain a grant by whatever route the artifact provides; how a request reaches a node that can grant, and how the grant comes back, is the artifact's business. **A requester** is a client that has taken a `request` step and has not yet received a grant in answer to it; a request or a grant lost on a down link does not end the client's standing as a requester.

**Rule E1, extended to reads.** In `quiescent`, "no request, write or ack is in flight" includes reads and read acks. The v3 addendum should have said so and did not.

**Rule E3, the bound.** A run that reaches `bound` before its end is reported `UNEXPLAINED bound`, never `PASS`. It is `FAIL C1.4` only if the side's liveness check witnesses the violation (on the model side a counterexample to the liveness property; on the impl side the liveness checker's report under Rule E1).

**Rule T3, unchanged and restated.** A `write` or `read` does not wait for an earlier unanswered `write` or `read` by the same client; only `request` waits for its own answer. A client that serialises its operations must not wait for ever on a reply that was lost.

Triggers may name `Fault` records for the new actions as for the old. Changelog: v4 (2026-10-21): `cut`, `drop`, L1 to L3, E1 extended to reads, E3, T3 restated. Reason: X2, failure model v2; the E1 gap, the readings in L3, E3 and T3 came from review of the inputs before any author started.

# Observability schema v1 (shared interface)

Fixed 2026-10-20 by the steward. `derives: C1.1, C1.2, C1.3, F1.1, F1.2, F1.3` (every clause and cell: this layer is what lets an unexplained failure be traced).

Both sides emit the same record, one JSON object per line, into `observe/<run>.jsonl`. The model side emits it from a TLC trace; the impl side emits it live.

## Record
```json
{"proc": "s", "seq": 17, "event": "WriteAccept",
 "key": "k", "token": 4, "highest_before": 3,
 "grantor_term": 2,
 "causes": [{"proc": "c1", "seq": 9}],
 "run": "false-suspicion-v1", "side": "impl"}
```
- `proc`, `seq`: the emitting process and its own counter. There is no cross-process clock and no wall-clock field in the record. Impl implementations may keep wall time in a separate file for humans; it is never used for ordering.
- `event` and its fields: exactly the observable events in `contract/v1.md`.
- `grantor_term`: on `Grant`, the term of the grantor that issued it; on `WriteAttempt`, `WriteAccept`, `WriteReject`, the term carried with the token. This is how a consequence is traced to the authority that produced it.
- `highest_before`: on storage decisions, the fence ledger's value when the decision was taken. The decision must be explainable from `token` and `highest_before` alone.
- `causes`: the records this one is a consequence of, by `(proc, seq)`. A `WriteAccept` causes the `WriteAttempt`; a `WriteAttempt` causes the `Grant` whose token it uses; a `WriteAck` causes the storage decision. A fault step from the schedule is recorded too, as an event `Fault` from `proc: "env"` with the step's action as fields, so a trace can show which fault preceded a consequence.

## The provenance question a trace must answer
For every `WriteAccept` and `WriteReject`: which `Grant`, from which `grantor_term`, produced the token presented, and what was the ledger when storage decided. If a trace cannot answer that for some decision, the observability layer has failed its own test, independently of the contract.

## v2 addendum (2026-10-21, for contract v2; additive)
The four read events from `contract/v2.md` are recorded with the same fields as their write counterparts, plus `value` on `ReadAccept` and on a served `ReadAck`. `causes` for a `ReadAccept` or `ReadReject` names the `ReadAttempt`; a `ReadAttempt` names the `Grant` whose token it uses; a `ReadAck` names the storage decision. The provenance question extends to reads: for every `ReadAccept` and `ReadReject`, which `Grant` and `grantor_term` produced the token, and what was the ledger when storage decided. `observe/provenance_check.py` is extended by the steward to check read decisions too.

## v3 addendum (2026-10-21, after X1; additive)
`WriteAck` and `ReadAck` carry a field `answers: {proc, seq}` naming the `WriteAttempt` or `ReadAttempt` they answer. It is redundant with `causes` (the storage decision, which in turn names the attempt) and is required anyway, so that a retried request's acks can be told apart without a traversal. Reason: the X1 regenerate-arm model author reported that without it a wrong ack is indistinguishable from a late one except through `causes`; tessera's finding E-02 (a timed-out signing request answered after its retry, two valid signatures for one presentation, nothing in the record naming which was which) is the same mechanism in a real service, cited from `docs/requests/2026-10-21-from-tessera-evidence-offer.md`. `observe/provenance_check.py` checks that `answers` names an attempt in the trace and that the ack's `causes` chain reaches the same attempt.

## v4 addendum (2026-10-21, for failure model v2; additive)
A `Fault` record for an F2.1 `cut` or F2.2 `drop` carries `links: [[from, to], ...]`, the **directed** links the step took down after selectors were resolved and self-pairs removed (a `cut` of `[a, b]` is recorded as `[a, b]` and `[b, a]`). A heal's `Fault` record carries `links: []` and `heal: true`. **Grants and retransmission.** A `Grant` record is a grant: each one is subject to C1.1 and must carry a token strictly greater than every earlier `Grant` record's. A grantor that re-sends a grant it has already recorded (because the reply may have been lost) does not record a second `Grant`; the resend is a retransmission, like a duplicate delivered by the network, and the client that receives it records nothing new. An artifact that instead issues a fresh grant records a new `Grant` with a higher token. Nothing else changes: the provenance question is the same, and `observe/provenance_check.py` needs no change, because link faults decide only which messages arrive, not where a token came from.

### The P10 fix (judge's verdict, locus: model)
The defect was the one the judge described.
1. n3 is elected for term 1 by the non-maximal majority {n1, n3}.
2. n1 crashes.
3. c1 requests.
4. Grant needs a majority promised to term 1, and only n3 is. Elect(n2) is disabled because n2 can reach a leader whose term is at least its own promise. StepDown(n3) is disabled because nobody has promised higher.
5. The model stutters with a majority, storage and the requester all up and connected.

The adapted model without the fix (commit `362f1ae`) reproduces this lasso on shared P10 state for state.

**Change.** A new action, `Join(n, q)`, under weak fairness. A leader `n` that can reach an up node `q` whose promise is below `n`'s term raises `promised[q]` to that term. If `q` was a stale leader, it stops leading. This is the abstract counterpart of a leader's heartbeat or append bringing a follower into its term.

**Why it is safe.**
- Promises only grow.
- A grant still needs a majority promised to exactly the leader's term.
- An election still takes `max(maxTok)` over a majority. Any grant's confirming majority intersects that majority, and each member of the intersection recorded the token before it raised its promise.

C1_1, C1_2 and C1_3 still hold on every shared schedule, and the mutations still break them.

**Not changed:** `C1_4`, `Good`, every fairness condition except the added `WF(Join)`, and every failure-model action. `derives: C1.4, F1.1, F1.2`

### Mutations, round 2
- **P11 re-placed.** The round-1 break (the request is consumed when the grant is issued) needs a grant reply to be lost across the cut. Shared P11 never loses one: the partition keeps the grantor and the holder together. Run once on shared P11, it printed `PASS`, as predicted.
  The new break is in `DoRequest`. A request made while the requester cannot reach a majority of lease nodes never reaches the grantor and is not retried after the heal, while the client keeps waiting. It sits on C1.4's path from request to grant, and it is specific to partitions. On shared P11 it prints `FAIL C1_4`.
- **P8 re-applied.** P8's edit now inserts its extra action into `Protocol` instead of replacing the whole definition, so the copy keeps `Join`. The break itself is unchanged.
- **Unchanged.** Every other mutation is unchanged and still fails on its shared schedule.

### New interpretations (round 2)
- **R2.1, T1 and an action's own event.** The event that step *i*−1's action emits is emitted after step *i* is armed, so it can satisfy step *i*'s trigger.
  Shared P11 needs this: step 5 `{event: Request, client: c1}` is satisfied by the Request emitted by step 4's own `request: c1`. Under the strict reading P11 could never end. `format v2 T1`
- **R2.2, E1 "in flight".** A message counts as in flight when its receiver is running. Acks and grant replies to a crashed or paused client are not counted, and neither are writes to a crashed storage.
  A write the client still awaits, but whose message was lost, is not in flight. The client simply never hears back.
  "No client is waiting for a grant" applies only to running, unpaused clients. `format v2 E1`
- **R2.3, A1 at run time.** "Resolved at the moment the step's trigger fires" is kept from round 1. If no Grant has happened by then, the alias names nothing, and the step waits for ever. The run is then UNEXPLAINED end unreachable, unless a violation is witnessed first. `format v2 A1`
- **R2.4, A2 with aliases.** The static check is conservative wherever an alias makes the target unknowable before running. `format v2 A2`
- **R2.5, the P10 fix as an interpretation of "the grantor".** The contract leaves how the nodes agree to the implementation. The model's abstract grantor must not lose liveness through its own bookkeeping, so it includes a leader bringing a lagging node into its term. Round 1 omitted this, and that was a modelling error, not a reading of the contract.

### What changed in `Lease.tla`
- **Connectivity is a set of directed links.**
  - `sideA` could express only a bipartition, so it is replaced by `down`, the set of pairs `<<p, q>>` whose link p→q is down. `down` derives from F1.2, F2.1 and F2.2.
  - `Link(p, q)` means p→q is up.
  - `Conn(p, q)` keeps its name but now means "connected" as `failure-model/v2.md` defines it: both directions of the direct link are up. It is not transitive.
  - F1.2 `partition` adds every crossing pair in both directions, which is F2.1's special case. `Cut` (F2.1) adds each listed pair in both directions. `Drop` (F2.2) adds each listed pair in the listed direction only.
  - `Heal(cell)` empties `down`, whichever cell it names (L2). Link failures accumulate until a heal.
  - This change is required by the meaning of F2.x.
- **A message's fate is fixed when it is sent.**
  - Each send checks the one directed link it uses, at the moment it is sent: client→storage for a write or read, storage→client for an ack.
  - `Partition` no longer removes messages already in flight.
  - Required by failure model v2, "Links".
- **The grantor, link by link.** Every change here is required by the meaning of F2.x.
  - `HearsLeader(x)`: some up leader m with `term[m] >= promised[x]` has m→x up.
  - `Elect(n)` needs `~HearsLeader(n)`. Its quorum must be connected to n, since a vote is a round trip.
  - **Voter stickiness (new).** Every voter must itself satisfy `~HearsLeader`. Tag: C1.4, F2.1.
  - `StepDown(n)` needs to hear q (q→n). `Join(n, q)` needs only n→q.
  - **`CheckQuorum(n)` (new).** A leader that is not connected to a majority of up lease nodes, itself included, stops leading. Tags: C1.4, F2.2, F2.1, F1.2.
  - `Grant(n, c)` still needs `Conn(n, c)` and a confirming majority that is connected to n. Both now mean "connected" in the v2 sense.
- **`Good(c)`, the premise of C1.4 (L3).**
  - Storage and c are up, c is not paused, and c and storage are connected.
  - Some majority Q of up lease nodes is pairwise connected, connected to storage, and connected to c.
  - Q need not contain the grantor. Under v1 bipartitions this is the old `Good(c)`.
- **TypeOK.** `down \subseteq Procs \X Procs`.

### Fairness (X2): every condition, and what justifies it
The brief's rule: weak fairness only on an action whose enablement depends on the acting process's own state and on messages over links that are up, and never on an action that requires having heard from a peer over a down link. Each condition below is checked against that rule.

| Condition | Enabled when | Justification |
|---|---|---|
| `WF(Elect(n))` | n hears no leader (its own election timer runs out); a majority is connected to n both ways and none of them hears a leader | Votes travel over up links in both directions. "Hears no leader" is the absence of messages, i.e. a timer in each voter's own state. Clauses: C1.4; cells F1.1, F1.2, F2.1, F2.2. |
| `WF(StepDown(n))` | a node with a higher promise is heard over q→n | A message over an up link. C1.4, C1.1. |
| `WF(CheckQuorum(n))` **(new)** | leader n is not connected to a majority | n's own timer: it has not heard from a majority. It does not require hearing anything. C1.4, F2.2. |
| `WF(Join(n, q))` | leader n, link n→q up, q lagging | n's message over an up link. C1.4 (P10 fix). |
| `WF(Grant(n, c))` | leader n; c's (retried) request arrives over c→n; reply over n→c; a majority connected to n confirms | Every message is over an up link. C1.4. |
| `WF(RecvGrant)`, `WF(RecvAck)`, `WF(RecvReadAck)` | a message is in flight to a running, unpaused receiver | The message was sent while its link was up, and failure model v2 says it is then delivered, even if the link has gone down since. |
| `WF(StorageDecide(_, FALSE))`, `WF(StorageRead(_, FALSE))` | a write or read is in flight to running storage | As above. |
| `WF(SendAck)`, `WF(SendReadAck)` | storage has a queued ack | Storage's own state. The send succeeds only if storage→client is up; if it is down the ack is lost, and fairness does not make it arrive. |
| `WF(ScheduleStep)` | the step's trigger has held | The environment does what the schedule says, as before. |

No liveness result rests on any other fairness. P25 and P26 pass because of `WF(CheckQuorum)` (P26) and voter stickiness, which is a protocol rule, not a fairness assumption (P25). Each depends only on these conditions.

### Interpretations (X2)
**New**
- **X2.1, the grantor's failure detector is directional.** A node hears a leader iff the leader→node link is up; "hears no leader" stands for an election timer. A vote and a grant confirmation are round trips, so both need connection. A step-down needs only to hear the higher promise; `Join` needs only to be heard.
- **X2.2, voter stickiness.** A node votes only if it hears no current leader itself.
  - This is my reading of how an artifact keeps C1.4 under F2.1. Without it, the follower cut off from the grantor in P19 and P25 is elected through the middle node. The old grantor then hears the higher promise through that node and steps down, and the cycle repeats. In the finite model, that would end at the term bound (UNEXPLAINED), not with a grant.
  - Consequence: on P19 the cut-off follower never becomes grantor. The pair says it "may", so the model takes the "may not" branch on every path, and every token in P19 comes from one leader.
- **X2.3, CheckQuorum.** Under F2.2 the followers can hear a grantor that cannot hear them (P20, P26). Their failure detector never fires, so the grantor must give up on its own. A leader not connected to a majority stops leading.
- **X2.4, grants go only to a connected requester.** `Grant(n, c)` needs `Conn(n, c)`.
  - A real grantor that hears a request over c→n while n→c is down would send its grant into the void. The model omits that behaviour (an under-approximation), because modelling it needs grant retransmission (observe v4) to stay finite.
  - No shared schedule has a requester that the grantor hears but cannot answer: P22 and P28 cut the lease nodes from a holder that is not requesting.
- **X2.5, no forwarding.** A request reaches a grantor only directly, and a grant comes back only directly.
  - L3 says a requester connected to a majority that excludes the grantor must still be granted "by whatever route the artifact provides". This model's route is that the grantor steps down (CheckQuorum) and the majority elects a node the requester is connected to.
  - The model would print `FAIL C1_4` on a schedule in which the requester is cut only from a grantor that keeps a majority, because nothing makes that grantor step down. No shared schedule is like that, so this is a limit of the model, not an observed result.
- **X2.6, `non-grantor` in a link.** All occurrences of `non-grantor` within one step resolve to the same node. Every candidate is explored, as in v2.1 A1.
- **X2.7, the cut's pairs in the Fault record.** The record carries both `cut`/`drop` (the listed pairs, resolved) and `links` (directed). The schema requires `links`; the step's action as fields follows the older schema text.

**Extended**
- **5 (grantor abstraction).** "Cannot reach a leader" becomes "does not hear a leader", by X2.1. Voters apply the same check (X2.2), and CheckQuorum is added (X2.3).
- **7 (grant retries).** As before, a lost grant reply leaves the request pending, and the next grant has a fresh token. In addition, a grant is issued only to a connected requester (X2.4).
- **12 (compiler rejections).** F2.1 and F2.2 are accepted. `rest` in a link is rejected, and so is a link entry that is not a pair.
- **17 (C1.4's condition).** "Connected" means direct and bidirectional, and the majority must be pairwise connected and connected to storage and to the requester (L3). Under v1 bipartitions this changes nothing.
- **20 (Fault records).** Extended with `links` and the heal record.
- **R2.2 (E1 "in flight").** A message sent while its link was up stays in flight after the link goes down, and is delivered. A message sent on a down link was never in flight.
- **R2.5 (Join).** It needs only the leader→node link.
- **TLC bounds.** `MaxTerm = 2 + 2 × (crash, restart, partition, heal, cut and drop steps)`. `TermHeadroom` held in all 31 runs.

**Contradicted**
- **13 (messages), "At the moment of a partition, messages whose endpoints end up on different sides are dropped."**
  - This no longer holds. Failure model v2: "a message sent while p→q is up is delivered (it may arrive late, reordered, after p→q has gone down)", and F1.2 is a special case of link failure.
  - Replaced by: each send checks its link when it is sent, and a later partition, cut or drop does not touch messages already in flight.
  - Effect on shared schedules: in P8, P17, P23 and P29, an ack or read ack that storage sent before the cut may still arrive. That only ever reports a decision storage really made. All four still PASS.
- **Model summary, "Environment", and README "Interpretations" 13, where they speak of "sides".** Read "sides" as the links an F1.2 partition takes down.

### Interpretations (X1)
- **X1.1, read identity.** A read is identified by (client, token, read id), and the read id is the schedule step index of the `read` step. Each read step is a distinct read; P17 issues three reads with the same token.
- **X1.2, C2.1's first sentence.** "At least the highest token storage has accepted" is checked against the history of accepted write tokens up to the read decision, not against storage's ledger variable. A forgetful ledger is caught (mutation P13).
- **X1.3, C2.1's second sentence.** "Serving a read does not change the highest accepted token" is checked on every read decision, served or rejected: the ledger after it equals the ledger before. No mutation exercises this half, as predicted. A read could only raise the ledger to its own token, which on these schedules is never above the ledger.
- **X1.4, C2.2's held value.** "The value storage held when it served" means `stval`, the value of the last accepted write, at the decision step. It is recorded as the ghost `held`, separately from the value storage returned, so a storage that returned something else would be caught. Before any write, the value is `"none"`; no shared schedule reads before writing.
- **X1.5, rejected reads.** A rejected read gives no value. Its `ReadAck` has outcome `rejected` and no `value` field, and `ReadReject` has no `value`.
- **X1.6, duplication.** Read deliveries may be duplicated under the same `MaxDups = 1` budget as writes. A duplicate read ack is ignored, because only an awaited read is acked to the client.
- **X1.7, reads and grants.** Reads never change a client's token or grant belief. `token: stale` for a read is defined exactly as for a write.
- **X1.8, mutation placement.**
  - P13's break, a volatile ledger, is P4's locus. The ledger is the one piece of state that enforces both C1.2 and C2.1, and P13's schedule exercises it only through a read.
  - P14 skips the read comparison.
  - P15 is an off-by-one "expiry grace" in the read comparison.
  - P16 acks a read before the volatile decision.
  - P17 is a client answering its own read while cut off.

## How to run
```
model/run.sh <schedule-name>   # e.g. P5, false-suspicion-v1; resolves only testbed/schedules/<name>.yaml [v2]
model/run.sh --mutations       # every mutation on its pair's schedule; each must print FAIL <its clause>
model/run.sh --all             # all 13 schedules, then all 12 mutations
```
It needs Java 11, `/home/tony/projects/tlaplus/tla2tools.jar` (override with `TLA2TOOLS=`) and `uv`.
`run.sh` pulls in `pyyaml==6.0.3` through `uv run --with`. `TLC_WORKERS` sets the TLC worker count (default 4).
A run prints exactly one line on stdout: `PASS`, `FAIL <invariant>` or `UNEXPLAINED <reason>`.
TLC statistics go to stderr. The observe file goes to `model/observe/<run>.jsonl`.
Scratch output (generated modules, raw TLC output) goes to `model/.work/`, which is git-ignored.

Pipeline for one run:
1. `compile.py` reads the schedule and writes `MC.tla` (the constants plus `Steps`), `MC.cfg`, `Witness.cfg` and `Done.cfg`.
2. TLC checks `MC.cfg`: invariants `TypeOK C1_1 C1_2 C1_3 TermHeadroom` and property `C1_4`.
3. On a PASS, TLC searches for a witness, i.e. a breadth-first, hence shortest, trace that completes the schedule and quiesces.
   `export.py` turns that trace into the observe file.
   On a FAIL, the counterexample becomes the observe file (`<pair>-mutation.jsonl` for mutation runs).
4. The run is UNEXPLAINED if any of these happens:
   - no trace reaches the schedule's end,
   - a witness's storage decision cannot be traced back to a Grant and grantor_term,
   - the `MaxTerm` bound is reached,
   - TLC reports anything other than a verdict.

## Model summary
- **Processes.** Three lease nodes, two clients and one storage process, with names taken from the schedule. The key is `"k"`.
- **Grantor.** Abstract: a leader per term.
  - Election: a node that cannot reach a leader whose term is at least its own promise may run an election.
    Any majority `Q` of up, reachable nodes promises the term `1 + max(promised over Q)`.
    The new leader starts from `max(maxTok over Q)`.
  - Grant: the leader issues token `ltok + 1` only when a majority that is still promised to its term confirms it.
    Each member of that majority durably records the token in `maxTok`.
  - Durable state: `promised` and `maxTok`. Volatile state: `leader`, `term` and `ltok`.
  - A leader that can reach a node promised to a higher term steps down.
  - **[v2]** A leader brings any reachable node whose promise is lower than its term into that term (`Join`).
- **Storage.** It accepts a write iff `token >= highest`, and on acceptance sets `highest := token`.
  The ledger and the value are durable.
  The ack is queued in volatile `toAck` and sent by a separate step, so a crash between accept and ack is possible.
- **Environment.** The actions are `Crash`, `Restart` (F1.1), `Partition`, `Heal` (F1.2) and `Pause`, `Resume` (F1.3).
  Each is tagged and reachable only through a schedule step.
- **Invariants.** They are stated over history variables (`grants`, `decisions`, `told`), not over the state they protect, so a component that forgets is caught:
  - `C1_1`: tokens strictly increase along the grant sequence.
  - `C1_2`: every accepted token is `>=` every previously accepted token.
  - `C1_3`: every write a client was told succeeded has an earlier accept decision for the same client, token and value.
- **Liveness.** `C1_4 == \A c : <>[]Good(c) => [](pending[c] => <>~pending[c])`, under weak fairness of every protocol action and of schedule steps.

## TLC bounds
- **Topology.** Fixed at 3 lease nodes, 2 clients, 1 storage and 1 key.
- **Terms.** `MaxTerm = 2 + 2 × (number of F1.1/F1.2 steps)`.
  `TermHeadroom` checks in every run that no reachable state uses the last allowed term, so the bound never constrains a behaviour.
  It held in all 13 runs. If it is ever reached, the run is UNEXPLAINED, not PASS.
- **Grants.** Bounded by requests: at most one grant per request step, plus a re-issue after a grant reply is lost to a fault.
  Requests per schedule: 1-3. The witnesses contain 1-3 grants.
- **Writes.** Exactly the schedule's write steps (0-4 per schedule), plus at most `MaxDups = 1` duplicated delivery of a write to storage.
  Duplicated grants and acks are not modelled; the client ignores them anyway (see interpretations).
- **Events.** The schedule's `bound: {events: 200}` is not needed as a TLC bound, because every run is finite by construction.
  The deepest state graph is 31 steps.
  The exporter warns if a trace exceeds `bound`; none does.

## Interpretations
Each item is a place where the inputs did not fix the answer, together with the choice made.

**Where things live**
1. **[v2] superseded by the format: shared schedules only.** **Schedule location.** `testbed/schedules/` did not exist, so I wrote all 13 schedules from `tests/pairs-v1.md` into `model/schedules/`.
   `run.sh` looks in `testbed/schedules/<name>.yaml` first, so a shared schedule replaces mine once it exists.
   The impl side will probably write its own versions of these schedules. Any difference between the two is itself a divergence to examine.
2. **Observe file location.** `observe/schema.md` names `observe/<run>.jsonl`. To avoid colliding with the impl side's file of the same name, the model writes `model/observe/<run>.jsonl` with `"side": "model"`.

**Time, expiry and pause**
3. **Time is abstract.** Grant lifetime is not a number in the model; `Lifetime = 1` is only the value reported on `Grant` events.
   - The grantor is not required to wait for a previous grant to expire before granting again. The contract states fencing properties (C1.1-C1.3), not mutual exclusion of holders.
   - An unpaused client's belief in its grant is never expired by the model. A schedule `write` uses the client's current token whatever its age.
4. **F1.3 pause.** "Paused past lifetime" is modelled as follows:
   - the paused client takes no steps (it receives no grants or acks) while every other process proceeds;
   - `resume` continues with the client's pre-pause state, including the token it believes is valid.
   - "Longer than the lifetime" is guaranteed by the schedule's trigger (for example, the resume fires on a later Grant to another client). The model has no clock to enforce it.
   - A paused client counts as not "up" in C1.4's condition.

**The grantor**
5. **[v2] with the P10 fix (`Join`), see R2.5.** **Grantor abstraction.**
   - Election and grant quorums may be any majority subset. They are not forced to be maximal.
   - A node runs an election only when it cannot reach a leader of a term at least its own promise. This is an abstract failure detector. It allows false suspicion under partition and prevents elections that would never end.
   - The token is a plain integer that the majority confirms. It is not term-encoded.
6. **[v2] now format rule T3.** **A request while waiting.** A client that is already waiting for a grant does not send a second request. The step waits until the earlier grant has arrived.
   This interpretation was adopted after a run: the first P1 witness merged two requests into one. The change tightened what the witness shows. Every verdict was the same before and after.
7. **Grant event and retries.**
   - `Grant` is recorded by the issuing lease node when it issues the grant, so a `{event: Grant}` trigger fires at issuance, not on receipt. A `write` step then waits until the client actually holds a token.
   - A lost grant reply is retried: the request stays pending until the client receives a grant, and the grantor may issue a new grant with a new token.
   - A grant reply that arrives when the client is no longer waiting is dropped.

**Schedules**
8. **[v2] now format rules T1, T2; see R2.1.** **Trigger semantics.** Steps are strictly sequential. Step *i*'s trigger is matched only against events emitted after step *i−1* was applied, including the event step *i−1* itself emitted. `start` fires immediately.
   This reads "both sides may act at any later point before the next step's trigger fires" as "the next trigger is not armed until this step is taken".
9. **[v2] see E1 and R2.2.** **End of a run.** The `end` trigger is matched after the last step. Ending stops the schedule's stimuli, but protocol steps continue, so in-flight work quiesces. Without this, C1.4 would be judged on runs cut off in the middle.
10. **[v2] now format rule A1.** **`grantor` and `holder`.**
    - They resolve to the node and the client of the most recent Grant at the moment the step's trigger fired.
    - The format mentions them only for partitions. I also accept them as the target of crash, restart, pause, resume and request.
    - `rest` is every process not named on the other side.
11. **`token: stale`.** The client's most recent token that is lower than the highest token granted so far, i.e. superseded. If the client has no such token, the step waits.
12. **Process names.** Process names come from the schedule. A schedule that is not exactly 3 lease nodes, 2 clients and 1 storage is rejected.
    The compiler also rejects:
    - a cell outside F1.1-F1.3;
    - an action that does not belong to its cell;
    - pausing a lease node;
    - a partition that does not have exactly two sides;
    - any other action not in the format.

**Faults and messages**
13. **Messages.**
    - Every channel is a set, so messages within a side may be reordered.
    - Only writes to storage are duplicated (at most once per run, `MaxDups = 1`). A duplicated grant or ack is ignored by the client: an ack counts only for a write it is still awaiting, and a grant only while the client is waiting.
    - At the moment of a partition, messages whose endpoints end up on different sides are dropped.
    - A message sent across an existing cut is lost.
    - A heal restores no lost message.
    - A message to a crashed process is lost.
14. **Crash.**
    - Storage crash: storage loses its inbox (in-flight writes) and its unsent acks. It keeps the ledger and the value.
    - Lease-node crash: the node loses its leadership state and keeps `promised` and `maxTok`.
    - Client crash: the client loses its token, every token it had received, its pending request and its awaited writes ("a restarted client has no grant").
    - "Storage replica" is read as the storage service, which is modelled as one process.

**The clauses**
15. **C1.2.** C1.2 is checked over the history of decisions, not over storage's own ledger variable, so a ledger that rolls back (mutation P4) is caught.
    "Records that token as the new highest" is not a separate invariant. A ledger that fails to record is caught when it accepts a lower token later (mutation P6).
16. **C1.3.** "Told a write succeeded" means the client recorded `WriteAck` with outcome `accepted`.
    The write is identified by (client, token, value). Values are unique within each schedule.
17. **C1.4, the condition.**
    - "A majority of lease nodes and storage stay up and connected to each other and to some requester" becomes `Good(c)`: storage is up, `c` is up and not paused, `c` and storage are on the same side, and some majority of lease nodes are up on that side.
    - "For long enough" is read as "eventually forever" (`<>[]Good(c)`).
    - Fairness is weak fairness on every protocol action and on schedule steps. The environment eventually performs each step whose trigger has held, so partitions heal when the schedule says so.
18. **C1.4, "obtains a grant".** This is read as "stops waiting". A crash also ends the wait; I read a crashed requester as no longer a requester. None of P10-P12 crashes the requester.

**Observe files**
19. **Witnesses.** An observe file for a PASS run is one sample: the shortest trace that completes the schedule and quiesces. It is not a summary of all behaviours.
    The exhaustive check is the verdict; the observe file is provenance for one run.
20. **What an observe record contains.**
    - Records are written in the model's trace order. The model has a total order; the file order is the only cross-process ordering the file carries, and no field records it.
    - `seq` is per process.
    - `causes` follow the schema. In addition, a `Grant` cites the `Request` it answers.
    - Internal steps (elections, step-downs, deliveries, sending an ack) are not observable events and are not emitted.
    - A `Fault` record is emitted from `proc: "env"`, with the action's resolved targets; a partition lists both sides.
    - For a liveness counterexample, the trace is the lasso's prefix; that the run stutters forever is reported on stderr, not in the file.

**Mutations**
21. **Mutation placement.**
    - P3's break (no increment) is not specific to F1.3: any second grant would expose it. It sits on C1.1's enforcing path, the increment, and P3's schedule exercises it through the paused holder's successor.
    - P7's break would also fail without the crash, because an ack sent before the decision is wrong on its own. The crash makes the lost decision permanent.

## Observations (not judgements)
- **False-suspicion witness** (`observe/false-suspicion-v1.jsonl`):
  1. The old holder c1 writes during the partition with token 1, after n2 had already granted token 2 (term 2) to c2.
  2. That write is accepted (`highest_before: 1`), because token 2 had not yet reached storage.
  3. After the heal, c2's token-2 write is accepted.
  4. c1's next token-1 write is then rejected (`highest_before: 2`).

  Every WriteAccept/WriteReject in the file names its token, its grantor_term and, through `causes`, the Grant it traces to.
  Fencing, as specified, allows a superseded holder to keep writing until a newer token reaches storage.

    pending,    \* derives: C1.4 -- pending[c]: c is waiting for (and retrying) a grant
    tok,        \* derives: C1.2, F1.3 -- c's current token [t, g] (g = grantor_term), volatile
    myToks,     \* derives: C1.2, F1.3 -- every token c has received since its last start
    awaiting,   \* derives: C1.3 -- writes c has sent and not yet had acked
    \* --- network (derives: F1.2, F2.1, F2.2; reorder by set semantics, duplication bounded by MaxDups;
    \*     a message is put in flight only if its link is up when it is sent, and once in flight it is
    \*     delivered whatever happens to the link later: failure model v2, "fate fixed when sent")
    grantMsgs,  \* derives: C1.1, F1.2 -- grant replies in flight, node -> client
    writeMsgs,  \* derives: C1.2, F1.2 -- writes in flight, client -> storage
    ackMsgs,    \* derives: C1.3, F1.2 -- acks in flight, storage -> client
    dups,       \* derives: C1.2, C1.3 -- duplicated deliveries used so far
    \* --- storage (derives: C1.2, C1.3)
    highest,    \* derives: C1.2, F1.1 -- durable fence ledger
    stval,      \* derives: C1.2 -- durable key value
    toAck,      \* derives: C1.3, F1.1 -- volatile: decided writes whose ack is not yet sent
    \* --- history (ghost) variables used only by invariants and the exporter
    grants,     \* derives: C1.1 -- sequence of every grant issued
    decisions,  \* derives: C1.2, C1.3 -- sequence of every storage decision
    told,       \* derives: C1.3 -- set of writes clients were told succeeded
    \* --- schedule driver (derives: F1.1, F1.2, F1.3)
    pc,         \* derives: F1.1, F1.2, F1.3 -- index of the next schedule step
    fired,      \* derives: F1.1, F1.2, F1.3 -- trigger of step pc has held since step pc-1
    trigG,      \* derives: F1.2, F1.3 -- most recent grant at trigger time (resolves grantor/holder)
    trigNG,     \* derives: F1.1; format v2.1 A1 -- lease nodes other than grantor up at trigger time
    ngDown,     \* derives: F1.1; format v2.2 A1, v2.1 A1 -- node crashed by the most recent `crash: non-grantor`
    lastEv,     \* derives: C1.1, C1.2, C1.3, C2.1, C2.2 -- the event emitted by the last step (for the exporter)
    \* --- reads (contract v2; derives: C2.1, C2.2)
    readMsgs,   \* derives: C2.1, F1.2 -- reads in flight, client -> storage
    rToAck,     \* derives: C2.2, F1.1 -- volatile: decided reads whose ack is not yet sent
    rAckMsgs,   \* derives: C2.2, F1.2 -- read acks in flight, storage -> client
    awaitingR,  \* derives: C2.2 -- reads c has sent and not yet had acked
    rdecisions, \* derives: C2.1, C2.2 -- history: every storage read decision
    given       \* derives: C2.2 -- history: every value a client was given

\* derives: C1.1, C1.2, C1.3, C1.4, F1.1, F1.2, F1.3 -- all state variables
vars == <<up, paused, down, promised, maxTok, leader, term, ltok, reqs,
          pending, tok, myToks, awaiting, grantMsgs, writeMsgs, ackMsgs, dups,
          highest, stval, toAck, grants, decisions, told, pc, fired, trigG, trigNG, ngDown, lastEv,
          readMsgs, rToAck, rAckMsgs, awaitingR, rdecisions, given>>

\* derives: C2.1, C2.2 -- the read variables, for UNCHANGED in actions that do not touch reads
rvars == <<readMsgs, rToAck, rAckMsgs, awaitingR, rdecisions, given>>

\* derives: F1.1, F1.2 -- every process
Procs == Nodes \cup Clients \cup {Store}

\* derives: C1.2, F1.3 -- "no token"
NoTok == [t |-> 0, g |-> 0]

\* derives: C1.1, C1.2
Max(S) == IF S = {} THEN 0 ELSE CHOOSE x \in S : \A y \in S : y <= x

\* derives: F1.2, F2.1, F2.2 (failure model v2 "Links") -- the link p->q is up. Self-pairs are
\* never down (format v4 L1), so Link(p, p) always holds.
Link(p, q) == <<p, q>> \notin down

\* derives: F1.2, F2.1, F2.2 (failure model v2 "Connected") -- p and q are connected: both
\* directions of the direct link are up. Not transitive. (Under v1 this was "same side".)
Conn(p, q) == Link(p, q) /\ Link(q, p)

\* derives: F2.1; format v4 cut -- each listed link in both directions
BothWays(L) == L \cup {<<x[2], x[1]>> : x \in L}

\* derives: C1.1, C1.4 -- majority of lease nodes
Majority(Q) == 2 * Cardinality(Q) > Cardinality(Nodes)

\* derives: C1.1, F1.2, F1.3 -- most recent Grant ("grantor" = its node, "holder" = its client)
LastGrant == IF grants = <<>> THEN [node |-> "none", client |-> "none"]
             ELSE [node |-> grants[Len(grants)].node, client |-> grants[Len(grants)].client]

\* derives: C1.1 -- highest token ever granted
MaxGranted == Max({grants[i].token : i \in 1..Len(grants)})

\* ---------------------------------------------------------------------------
\* Schedule triggers
\* derives: F1.1, F1.2, F1.3
Trig(i) == IF i <= Len(Steps) THEN Steps[i].trig ELSE EndTrig
\* derives: F1.1, F1.2, F1.3
IsStart(T) == T.event = "start"
\* derives: F1.1, F1.2, F1.3; format v2.1 T1 -- an event matches a trigger: same event and every
\* filter field equal. Only events emitted while the trigger is armed are ever offered to it
\* (Emit and ScheduleStep), which is T1's "matches only events emitted after it was armed".
\* `quiescent` (E1) is a state predicate, never matched by an event.
Matches(T, e) == /\ T.event \notin {"start", "quiescent"}
                 /\ e.event = T.event
                 /\ \A f \in (DOMAIN T) \ {"event"} : f \in DOMAIN e /\ e[f] = T[f]

\* derives: C1.1, C1.2, C1.3, F1.1, F1.2, F1.3
\* Protocol step emitting event e: record it, and advance the current trigger.
\* Must be the last conjunct of an action (uses grants').
Emit(e) == /\ lastEv' = e
           /\ fired' = (fired \/ Matches(Trig(pc), e))
           /\ trigG' = IF ~fired /\ Matches(Trig(pc), e) THEN LastGrant' ELSE trigG
           /\ trigNG' = IF ~fired /\ Matches(Trig(pc), e)
                        THEN {n \in Nodes : up'[n]} \ {LastGrant'.node} ELSE trigNG
           /\ UNCHANGED <<pc, ngDown>>

\* derives: C1.1, C1.4 -- internal (non-observable) protocol step
Internal(what, p) == Emit([event |-> "Internal", what |-> what, proc |-> p])

\* derives: C1.1, C1.2, C1.3, C1.4, F1.1, F1.2, F1.3
Init ==
    /\ up = [p \in Procs |-> TRUE]
    /\ paused = [c \in Clients |-> FALSE]
    /\ down = {}           \* derives: F1.2, F2.1, F2.2 -- every link up
    /\ promised = [n \in Nodes |-> 0]
    /\ maxTok = [n \in Nodes |-> 0]
    /\ leader = [n \in Nodes |-> FALSE]
    /\ term = [n \in Nodes |-> 0]
    /\ ltok = [n \in Nodes |-> 0]
    /\ reqs = {}
    /\ pending = [c \in Clients |-> FALSE]
    /\ tok = [c \in Clients |-> NoTok]
    /\ myToks = [c \in Clients |-> {}]
    /\ awaiting = [c \in Clients |-> {}]
    /\ grantMsgs = {}
    /\ writeMsgs = {}
    /\ ackMsgs = {}
    /\ dups = 0
    /\ highest = 0
    /\ stval = "none"
    /\ toAck = {}
    /\ grants = <<>>
    /\ decisions = <<>>
    /\ told = {}
    /\ pc = 1
    /\ fired = IsStart(Trig(1))
    /\ trigG = [node |-> "none", client |-> "none"]
    /\ trigNG = Nodes
    /\ ngDown = "none"
    /\ readMsgs = {}       \* derives: C2.1
    /\ rToAck = {}         \* derives: C2.2
    /\ rAckMsgs = {}       \* derives: C2.2
    /\ awaitingR = [c \in Clients |-> {}]   \* derives: C2.2
    /\ rdecisions = <<>>   \* derives: C2.1, C2.2
    /\ given = {}          \* derives: C2.2
    /\ lastEv = [event |-> "Init"]

\* ===========================================================================
\* Grantor (abstract): leader per term, majority election, majority-confirmed grants
\* ===========================================================================

\* derives: C1.1, C1.4, F1.2, F2.1, F2.2 -- node x hears a current leader: an up leader m
\* whose term is at least x's promise, over the link m->x (hearing is directional: F2.2).
\* A leader hears itself.
HearsLeader(x) == \E m \in Nodes : up[m] /\ Link(m, x) /\ leader[m] /\ term[m] >= promised[x]

\* derives: C1.1, C1.4, F1.1, F1.2, F2.1, F2.2
\* A node that hears no leader of a term at least its own promise starts an election;
\* a majority Q (up, connected to n both ways: a vote is a round trip) promises a fresh
\* term; the new leader learns the highest token any member of Q confirmed.
\* X2: each voter must itself hear no current leader (voter stickiness, a pre-vote check).
\* derives: C1.4, F2.1 -- under F2.1 a follower cut off from a grantor that still has a
\* majority can reach a node that still hears it; the voter refuses, so the cut-off
\* follower cannot disrupt the grantor (P19, P25). Under v1 bipartitions every node a
\* candidate could reach was on its side and heard no leader either.
Elect(n) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[n] /\ ~leader[n]
    /\ ~HearsLeader(n)
    /\ \E Q \in SUBSET {q \in Nodes : up[q] /\ Conn(n, q)} :
        /\ n \in Q
        /\ Majority(Q)
        /\ \A q \in Q : ~HearsLeader(q)   \* derives: C1.4, F2.1 -- voter stickiness
        /\ LET t == 1 + Max({promised[q] : q \in Q}) IN
           /\ t <= MaxTerm
           /\ promised' = [q \in Nodes |-> IF q \in Q THEN t ELSE promised[q]]
           /\ leader' = [q \in Nodes |-> IF q = n THEN TRUE
                                         ELSE IF q \in Q THEN FALSE ELSE leader[q]]
           /\ term' = [term EXCEPT ![n] = t]
           /\ ltok' = [ltok EXCEPT ![n] = Max({maxTok[q] : q \in Q})]
    /\ UNCHANGED <<up, paused, down, maxTok, reqs, pending, tok, myToks, awaiting,
                   grantMsgs, writeMsgs, ackMsgs, dups, highest, stval, toAck,
                   grants, decisions, told>>
    /\ Internal("Elect", n)

\* derives: C1.1, C1.4, F1.2, F2.2 -- a leader that hears a node promised to a higher term steps
\* down (it needs only q->n: the higher promise reaches it in q's message)
StepDown(n) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[n] /\ leader[n]
    /\ \E q \in Nodes : up[q] /\ Link(q, n) /\ promised[q] > term[n]
    /\ leader' = [leader EXCEPT ![n] = FALSE]
    /\ promised' = [promised EXCEPT ![n] =
                      Max({promised[q] : q \in {x \in Nodes : up[x] /\ Link(x, n)}})]
    /\ UNCHANGED <<up, paused, down, maxTok, term, ltok, reqs, pending, tok, myToks,
                   awaiting, grantMsgs, writeMsgs, ackMsgs, dups, highest, stval,
                   toAck, grants, decisions, told>>
    /\ Internal("StepDown", n)

\* derives: C1.4, F1.1, F1.2, F2.2 -- the P10 fix (judge's verdict, locus: model).
\* X2: it needs only the link n->q (the leader's message reaches q).
\* A leader brings a reachable, up, lagging node into its term: the node raises its
\* promise to the leader's term (and, if it was a stale leader, stops leading).
\* Without this, a leader elected by a non-maximal majority whose other member then
\* crashes can never assemble a grant majority, while no election or step-down is
\* enabled either: C1.4 fails with a majority, storage and the requester all up and
\* connected. Raising a promise is always safe here: promises only grow, and a grant
\* still needs a majority promised to exactly the leader's term.
Join(n, q) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[n] /\ leader[n] /\ up[q] /\ q # n
    /\ Link(n, q)
    /\ promised[q] < term[n]
    /\ promised' = [promised EXCEPT ![q] = term[n]]
    /\ leader' = [leader EXCEPT ![q] = FALSE]
    /\ UNCHANGED <<up, paused, down, maxTok, term, ltok, reqs, pending, tok, myToks,
                   awaiting, grantMsgs, writeMsgs, ackMsgs, dups, highest, stval,
                   toAck, grants, decisions, told>>
    /\ Internal("Join", q)

\* derives: C1.4, F2.2, F2.1, F1.2 -- the quorum check (new in X2). A leader that is not
\* connected (both ways) to a majority of up lease nodes, itself included, stops leading.
\* Under F2.2 the followers may still hear a grantor that cannot hear them; their
\* failure detector then never fires and, without this, nobody would ever elect (P26).
\* Under v1 it only lets a grantor isolated in a minority stop sooner.
CheckQuorum(n) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[n] /\ leader[n]
    /\ ~Majority({q \in Nodes : up[q] /\ Conn(n, q)})
    /\ leader' = [leader EXCEPT ![n] = FALSE]
    /\ UNCHANGED <<up, paused, down, promised, maxTok, term, ltok, reqs, pending, tok, myToks,
                   awaiting, grantMsgs, writeMsgs, ackMsgs, dups, highest, stval,
                   toAck, grants, decisions, told>>
    /\ Internal("CheckQuorum", n)

\* derives: C1.1, C1.4, F1.1, F1.2, F2.1, F2.2
\* The leader issues a grant to a requester it is connected to (the retried request
\* arrives over c->n, the reply leaves over n->c), once a majority still promised to its
\* term, and connected to it (a confirmation is a round trip), durably confirms the token.
Grant(n, c) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[n] /\ leader[n]
    /\ c \in reqs
    /\ Conn(n, c)
    /\ ~\E m \in grantMsgs : m.c = c
    /\ \E Q \in SUBSET {q \in Nodes : up[q] /\ Conn(n, q) /\ promised[q] = term[n]} :
        /\ n \in Q
        /\ Majority(Q)
        /\ LET k == ltok[n] + 1 IN
           /\ maxTok' = [q \in Nodes |-> IF q \in Q THEN Max({maxTok[q], k}) ELSE maxTok[q]]
           /\ ltok' = [ltok EXCEPT ![n] = k]
           /\ grantMsgs' = grantMsgs \cup {[n |-> n, c |-> c, t |-> k, g |-> term[n]]}
           /\ grants' = Append(grants, [token |-> k, term |-> term[n], node |-> n, client |-> c])
           /\ UNCHANGED <<up, paused, down, promised, leader, term, reqs, pending, tok,
                          myToks, awaiting, writeMsgs, ackMsgs, dups, highest, stval,
                          toAck, decisions, told>>
           /\ Emit([event |-> "Grant", client |-> c, key |-> Key, token |-> k,
                    lifetime |-> Lifetime, grantor_term |-> term[n], node |-> n])

\* derives: C1.4, F1.3 -- a (running, unpaused) client receives a grant reply
RecvGrant(m) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ m \in grantMsgs
    /\ up[m.c] /\ ~paused[m.c]
    /\ grantMsgs' = grantMsgs \ {m}
    /\ IF pending[m.c]
       THEN /\ tok' = [tok EXCEPT ![m.c] = [t |-> m.t, g |-> m.g]]
            /\ myToks' = [myToks EXCEPT ![m.c] = @ \cup {[t |-> m.t, g |-> m.g]}]
            /\ pending' = [pending EXCEPT ![m.c] = FALSE]
            /\ reqs' = reqs \ {m.c}
       ELSE UNCHANGED <<tok, myToks, pending, reqs>>
    /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, awaiting,
                   writeMsgs, ackMsgs, dups, highest, stval, toAck, grants, decisions, told>>
    /\ Internal("RecvGrant", m.c)

\* ===========================================================================
\* Storage
\* ===========================================================================

\* derives: C1.2, C1.3, F1.1
\* Storage decides a write: accept iff token >= ledger; on accept the token becomes
\* the ledger. The ack is queued (volatile) and sent by SendAck. dup = TRUE models a
\* duplicated delivery (the message stays in flight), bounded by MaxDups.
StorageDecide(m, dup) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[Store]
    /\ m \in writeMsgs
    /\ dup => dups < MaxDups
    /\ LET acc == m.t >= highest
           out == IF acc THEN "accept" ELSE "reject" IN
       /\ highest' = IF acc THEN m.t ELSE highest
       /\ stval' = IF acc THEN m.v ELSE stval
       /\ writeMsgs' = IF dup THEN writeMsgs ELSE writeMsgs \ {m}
       /\ dups' = IF dup THEN dups + 1 ELSE dups
       /\ decisions' = Append(decisions, [token |-> m.t, hb |-> highest, outcome |-> out,
                                          client |-> m.c, value |-> m.v, term |-> m.g])
       /\ toAck' = toAck \cup {[c |-> m.c, t |-> m.t, g |-> m.g, v |-> m.v, outcome |-> out]}
       /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, reqs,
                      pending, tok, myToks, awaiting, grantMsgs, ackMsgs, grants, told>>
       /\ Emit([event |-> IF acc THEN "WriteAccept" ELSE "WriteReject", key |-> Key,
                token |-> m.t, highest_before |-> highest, grantor_term |-> m.g,
                client |-> m.c, value |-> m.v])

\* derives: C1.3, F1.1, F1.2, F2.1, F2.2 -- storage sends a queued ack (lost if the link
\* storage->client is down or the client is down, at the moment it is sent)
SendAck(a) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[Store]
    /\ a \in toAck
    /\ toAck' = toAck \ {a}
    /\ ackMsgs' = IF Link(Store, a.c) /\ up[a.c] THEN ackMsgs \cup {a} ELSE ackMsgs
    /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, reqs, pending,
                   tok, myToks, awaiting, grantMsgs, writeMsgs, dups, highest, stval,
                   grants, decisions, told>>
    /\ Internal("SendAck", Store)

\* derives: C1.3, F1.3 -- a client receives an ack for a write it is awaiting
\* and is told the write's outcome exactly as the ack states it.
RecvAck(a) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ a \in ackMsgs
    /\ up[a.c] /\ ~paused[a.c]
    /\ ackMsgs' = ackMsgs \ {a}
    /\ LET w == [t |-> a.t, g |-> a.g, v |-> a.v] IN
       IF w \in awaiting[a.c]
       THEN /\ awaiting' = [awaiting EXCEPT ![a.c] = @ \ {w}]
            /\ told' = IF a.outcome = "accept" THEN told \cup {[c |-> a.c, t |-> a.t, v |-> a.v]}
                       ELSE told
            /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, reqs,
                           pending, tok, myToks, grantMsgs, writeMsgs, dups, highest,
                           stval, toAck, grants, decisions>>
            /\ Emit([event |-> "WriteAck", client |-> a.c, key |-> Key, token |-> a.t,
                     outcome |-> IF a.outcome = "accept" THEN "accepted" ELSE "rejected",
                     value |-> a.v, grantor_term |-> a.g])
       ELSE /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, reqs,
                           pending, tok, myToks, awaiting, grantMsgs, writeMsgs, dups,
                           highest, stval, toAck, grants, decisions, told>>
            /\ Internal("DropAck", a.c)

\* ===========================================================================
\* Schedule steps: workload (derives from the contract) and faults (one per cell)
\* ===========================================================================

\* derives: F1.1, F1.2, F1.3; format v2.1 A1 -- resolve "grantor"/"holder"/"non-grantor" at trigger time
\* format v2.1 A1: `non-grantor` resolves to ng, one of the candidates chosen by ScheduleStep
Resolve(x, ng) == IF x = "grantor" THEN trigG.node
                  ELSE IF x = "holder" THEN trigG.client
                  ELSE IF x = "non-grantor" THEN ng ELSE x

\* derives: C1.2, F1.3 -- the client's most recent superseded token (lower than the highest granted)
StaleTok(c) ==
    LET S == {x \in myToks[c] : x.t < MaxGranted} IN
    IF S = {} THEN NoTok ELSE CHOOSE x \in S : \A y \in S : y.t <= x.t

\* derives: C1.4 -- workload: client requests a grant (a client already waiting for
\* a grant does not issue a second request; the step waits until it is not waiting)
DoRequest(c) ==
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[c] /\ ~paused[c]
    /\ ~pending[c]
    /\ pending' = [pending EXCEPT ![c] = TRUE]
    /\ reqs' = reqs \cup {c}
    /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, tok, myToks,
                   awaiting, grantMsgs, writeMsgs, ackMsgs, dups, highest, stval, toAck,
                   grants, decisions, told>>
    /\ lastEv' = [event |-> "Request", client |-> c, key |-> Key]

\* derives: C1.2, C1.3, F1.3, F2.1, F2.2 -- workload: client writes with its current (or stale)
\* token; the write is lost if client->storage is down when it is sent
DoWrite(c, v, stale) ==
    LET k == IF stale THEN StaleTok(c) ELSE tok[c] IN
    /\ UNCHANGED rvars  \* derives: C2.1, C2.2 -- reads untouched
    /\ up[c] /\ ~paused[c]
    /\ k.t > 0
    /\ writeMsgs' = IF Link(c, Store) /\ up[Store]
                    THEN writeMsgs \cup {[c |-> c, t |-> k.t, g |-> k.g, v |-> v]}
                    ELSE writeMsgs
    /\ awaiting' = [awaiting EXCEPT ![c] = @ \cup {[t |-> k.t, g |-> k.g, v |-> v]}]
    /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, reqs, pending,
                   tok, myToks, grantMsgs, ackMsgs, dups, highest, stval, toAck,
                   grants, decisions, told>>
    /\ lastEv' = [event |-> "WriteAttempt", client |-> c, key |-> Key, token |-> k.t,
                  value |-> v, grantor_term |-> k.g]

\* ===========================================================================
\* Reads (contract v2, X1)
\* ===========================================================================

\* derives: C2.1, C2.2, F1.1 -- storage decides a read: serve iff token >= ledger, returning
\* the value it holds; the ledger is not changed. The ack is queued (volatile).
\* dup = TRUE models a duplicated delivery (bounded by MaxDups, shared with writes).
StorageRead(m, dup) ==
    /\ up[Store]
    /\ m \in readMsgs
    /\ dup => dups < MaxDups
    /\ LET srv == m.t >= highest
           out == IF srv THEN "served" ELSE "rejected"
           val == IF srv THEN stval ELSE "none" IN
       /\ UNCHANGED <<rAckMsgs, awaitingR, given>>
       /\ UNCHANGED <<up, paused, down, promised, maxTok, leader, term, ltok, reqs,
                      pending, tok, myToks, awaiting, grantMsgs, writeMsgs, ackMsgs,
                      highest, stval, toAck, grants, decisions, told>>
       /\ readMsgs' = IF dup THEN readMsgs ELSE readMsgs \ {m}
       /\ dups' = IF dup THEN dups + 1 ELSE dups
       /\ rdecisions' = Append(rdecisions,
                [token |-> m.t, hb |-> highest, ha |-> highest', outcome |-> out, client |-> m.c,
                 rid |-> m.r, value |-> val, held |-> stval, nwrites |-> Len(decisions)])
       /\ rToAck' = rToAck \cup {[c |-> m.c, t |-> m.t, g |-> m.g, r |-> m.r,
                                  outcome |-> out, v |-> val]}
       /\ Emit(IF srv
                THEN [event |-> "ReadAccept", key |-> Key, token |-> m.t, highest_before |-> highest,
                      value |-> val, grantor_term |-> m.g, client |-> m.c, rid |-> m.r]
                ELSE [event |-> "ReadReject", key |-> Key, token |-> m.t, highest_before |-> highest,
                      grantor_term |-> m.g, client |-> m.c, rid |-> m.r])

\* derives: C2.2, F1.1, F1.2, F2.1, F2.2 -- storage sends a queued read ack (lost if the link
\* storage->client is down or the client is down, at the moment it is sent)
SendReadAck(a) ==
    /\ up[Store]
    /\ a \in rToAck
    /\ rToAck' = rToAck \ {a}

## M1 design and plan (historical)

<!-- derives: C1.1, C1.2, C1.3, C1.4, F1.1, F1.2, F1.3 -->
Use the existing HashiCorp Raft protocol with three nodes and durable in-memory
log/stable stores retained across node replacement. A committed FSM command
allocates each token. Two clients and one storage execute in the same OS process.
Storage retains its ledger across replacement; restarted clients lose grants.
Disconnect Raft transports and gate all client/storage traffic across a complete
bipartition. Pauses freeze client activity, while grant lifetimes continue.

Alternatives considered: an external multi-process deployment makes fault runs
slower and harder to reproduce; implementing a new quorum protocol violates the
brief. The selected in-process Raft arrangement uses a real existing protocol
with an independently implemented event-log checker.

Implementation sequence: (1) preregister and commit predictions and scoring;
(2) implement Raft, clients, storage, injectors and causal emitter; (3) implement
strict YAML compiler, all thirteen schedules, independent checkers and mutation
runner; (4) run the preregistered baseline/mutation matrix, document any
outcome-informed amendments additively; (5) commit the first complete version.

## M1 interpretations (historical)

<!-- derives: C1.1, C1.2, C1.3, C1.4, F1.1, F1.2, F1.3 -->
1. All generated artifacts, including the shared relative `testbed/schedules/`
   and `observe/` paths, live beneath `impl/` to respect the brief's output scope.
2. A grant is an observable committed reply. Failed or timed-out Raft operations
   may consume tokens without issuing grants. Integer gaps are permitted.
3. The contract does not require exclusive holders or specify renewal. This
   implementation waits at least the prior issued lifetime before issuing the
   next grant, making a later grant an expiry witness for pause/resume schedules.
4. Durable state is an in-memory object that survives simulated process
   replacement, not OS termination. Raft log/stable stores and storage's ledger
   survive; clients' volatile grants and pending reply inboxes do not.
5. Timeouts and real elapsed time drive the execution only. Checkers never order
   records by wall clock or by cross-process line order. Causal references and
   process sequence numbers determine observable order.
6. The schema's prose says a WriteAccept 'causes' a WriteAttempt, but its example
   and causal intent imply references point backwards: decision -> attempt ->
   grant -> request, and ack -> decision. We implement backwards references.
7. C1.1 concurrent grants without causal order are unorderable from this schema.
   The runner serializes successful grants through the grantor and links the
   previous grant into the next grant, including across incarnations. The
   checker rejects missing order evidence as UNEXPLAINED, not as a violation.
8. Liveness is tested with a finite three-second progress opportunity after
   eligible pending requests and stable connectivity. A qualifying unfulfilled
   request at that horizon fails C1.4; an unreachable schedule trigger without
   such a witness is UNEXPLAINED. This is a bounded operational interpretation
   of 'long enough', not proof of unbounded eventuality.
9. A paused holder may intentionally submit its old token after resumption;
   fencing, rather than the client's expiry check, is the protection being tested.
   `token: stale` chooses its newest superseded or expired grant and is rejected
   as an invalid workload if no such grant exists.
10. Trigger predicates remain true once observed, as the format states. Repeated
    `start` triggers are immediately enabled. Actions are serialized and fault
    events include causal trigger references. End is checked after all actions.
11. Messages crossing a cut are lost, including accept replies. Within-side
    duplicate write deliveries retain the original attempt reference. Successful
    late replies are correlated to their actual storage decision; client restart
    discards its old inbox. Paused clients retain their inbox until resumed.
12. The false-suspicion topology is exactly old grantor + c1 + storage against
    the remaining nodes + c2. It heals before c2 writes because storage is on
    c1's side during the cut. Its trace receives provenance validation and is
    reported as observed; ordinary contract results remain separately visible.
13. The same half-open lifetime applies to all grants (40 ms). Requests are
    retried against reachable leaders; a minority cannot issue a committed grant.
    Raft timers are operational and excluded from the observable record.
14. Crash/restart actions name explicit process IDs. Dynamic `grantor`, `holder`
    and `rest` aliases are supported in partition membership only, per format.

## Additional interpretations from source review (no outcomes)

<!-- derives: C1.1, C1.2, C1.3, C1.4, F1.1, F1.2, F1.3 -->
15. Tokens are committed Raft log indices, rather than a separate persistent
    counter. Configuration and election entries cause legal gaps. The term is
    the committed entry's Raft term. FSM snapshots retain the last allocation.
16. The three-second C1.4 opportunity cannot be inferred from a clock-free finite
    event log alone. The runner writes a separate `<run>.meta.json` certificate
    naming each pending request, the last fault reference and the stable budget.
    The checker independently verifies final connectivity and lack of a grant
    from the JSONL, but trusts the runner's duration certificate. This limitation
    is explicit; a timeout without a certificate is UNEXPLAINED. Offline checking
    uses `impl/run.sh P10 --check observe/<run>.jsonl` from the repository root,
    with paths relative to `impl/`; `--evidence` overrides the sidecar path.
17. An ack missing its acceptance reference is UNEXPLAINED when an acceptance for
    that exact attempt exists elsewhere in the trace. A ghost ack for a distinct
    attempt with no acceptance is a C1.3 failure even if another write with the
    same token was accepted. Duplicate deliveries of one attempt may each have
    a decision. The P7/P8 schedules therefore contain both an accepted write with
    a lost reply and a second write that never reaches storage.
18. Observe sequence numbers survive simulated process restart in the observer.
    They are instrumentation state, not recovered grant authority. Followers
    emit no synthetic contract events: a lease node emits a Grant when it issues
    one; all fault actions are emitted by env. 'From every process' means every
    process producing a contract event uses its own sequence, not that idle
    followers invent events outside the schema.
19. Fault records include resolved partition memberships, so alias meanings are
    recoverable directly from the trace. The original YAML retains the aliases.
    The schedule compiler rejects omitted, repeated or unresolved members and
    rejects unknown cells, fields and operations before starting the workload.
20. The runner serializes request completion and spaces grants as a workload
    policy. After a pause it waits at least a further full lifetime before the
    next grant, guaranteeing a later Grant witnesses the required pause duration.
    This timing policy is not a replacement consensus protocol or a safety
    assumption of the Raft token allocator. The observer's prior-grant reference
    records the harness's serial causal chain; it does not carry allocation
    authority between partitioned nodes.
21. Sampling covers 1–5 ms delivery jitter, 25–39 ms Raft RPC timeouts, shuffled
    due-message batches, and a one-in-three chance of a duplicate write delivery.
    Ack delivery adds 8 ms plus jitter, so a fault triggered by a decision can
    intervene. Initial grants also depend on Raft's internal election randomness.
    Network messages are gated at delivery and cut creation, so healing does not
    resurrect messages discarded across the cut. This samples a subset of the
    permitted nondeterminism and does not explore arbitrary Raft message
    duplication or every possible action delay.
22. End predicates are checked after all actions to prevent historical matches
    from skipping required actions. A final 50 ms drain observes in-flight
    replies; a step waiting for an absent trigger has a five-second operational
    guard. The event bound also stops the runner. Clause violations already
    witnessed in a partial trace remain failures even if a later trigger is
    unreachable; an absent trigger alone never kills a mutation.
23. Baseline storage starts with a zero fence for positive allocated tokens, and
    retains the last accepted value as well as the fence through storage crashes.
    Negative or arbitrary externally forged tokens are not workload actions in
    the shared format. The contract's integer tokens are represented by uint64
    Raft indices; exhausting that representation is outside these bounded runs.
24. The preregistration gate in `run.sh` requires the preregistration file in HEAD
    before it builds or runs the program. No model/implementation comparison or
    correctness attribution is performed by this author. Mutation kills are
    scored only against the predeclared clause. The schema does not itself encode
    elapsed duration, so the sidecar is a limitation of bounded liveness scoring.

<!-- derives: C1.1, C1.3, C1.4, F1.1, F1.2 -->
25. The final transport is a small adapter for HashiCorp Raft's existing RPC
    interface, using locked in-memory inboxes. It has no consensus or allocation
    logic. It atomically checks connectivity when sending, tracks endpoint
    incarnations and cut history, and gates replies separately. Pipelining is
    disabled through Raft's supported fallback. Requests delivered into an inbox
    before a cut may still be processed, but their replies are independently
    subject to the cut. Client writes sent during a cut are dropped immediately,
    even if healing precedes their sampled delivery deadline. Adapter fixtures
    separately cover lost sends, cut/heal replies, unaffected majority traffic
    and process replacement. The 1024-entry inbox is an operational resource
    limit; exhaustion is not a new admitted failure cell and must be treated as
    an operational limitation if encountered.
