# X3 measure 10: what each check is expected to flag, per hook class (registered before hold-outs)

Written 2026-10-25 by the seventh steward, before any hold-out, plant or hook exists, from `observe/decision_replay.py` (draft 5, as committed), `observe/provenance_check.py`, `observe/schema.md` and `contract/v3.md`. derives: X3 prereg measure 10 and X3-7; Fable prereg review finding 9; sixth handoff, owed item 1.

**How the steward adds a hook (registered):** the hook changes the implementation's state or delivery, in service code; the implementation's recording code is not touched, so records report the hooked state truthfully. A hook that made records disagree with state would test the checks against forgery, a different question, and is not done.

**What the checks can see, read from their code.** Part 1 checks each storage decision against its own recorded inputs (`token`, `ledger`, `stored_value`) only; nothing compares the ledger across storage's records. Part 2 orders a lease node's `Agree` records by its own `(inc, seq)`; `inc` changes only on an amnesic restart, and `seq` continues across an ordinary one (schema, Identity), so part 2's order spans ordinary restarts. Part 3 compares outcomes of equal inputs across runs. Provenance follows each storage decision's `causes` to a `Grant` with its token and term.

| Hook class | Part 1 | Part 2 | Part 3 | Provenance | Expected (i) |
|---|---|---|---|---|---|
| **Ledger rollback** (storage's ledger set below a token it has accepted, no restart) | silent: each later decision agrees with the rolled-back ledger it records | silent (grants untouched) | silent unless another run has a decision with equal inputs and a different outcome; the rollback changes inputs, not the function | silent | **no check flags it, by design.** A C1.2 violation (an accept below a token accepted earlier) is visible only across storage's own records, which no check compares. A result for the schema. |
| **Storage restart from an older state** (storage restarts with ledger and value of an earlier point) | silent, as above; served reads return the old `stored_value`, which they record | silent | silent, as above | silent | **no check flags it, by design**, same reason; the restart is visible as storage's `inc` increasing, and C2.2 is not violated by the record (the value given is the value held). A result for the schema. |
| **Lost durable record at a lease node** (an ordinary restart that keeps all but one record the node wrote durably) | flags only if the loss makes the node take part in a decision whose evidence fails (e.g. a `Grant` whose `members` are not the committed configuration, after a lost `ConfigCommitted`) | **flags** if, after the restart, the node's counted `Agree` carries a token not above one it agreed to before (C1.1 per-node order), or a token is granted twice | flags if the loss changes an outcome for inputs equal to another run's | silent | **flagged iff the loss has a consequence in the trace** (the schedule must exercise a decision after the restart that depends on the lost record); otherwise latent, and (i) is "no" with the reason stated. Expected: part 2. |
| **Duplicated grant reply delivered after a newer grant** (the client receives the old `Grant` reply again after a newer token was granted) | silent: storage still fences | silent: no second `Grant` record is emitted (the reply is duplicated, not the decision) | silent | silent: the client's attempt still chains to the real `Grant` | **no check flags it, and no clause of contract v3 is violated** as long as storage fences: an older holder writing before a newer token is accepted is allowed ("Fencing"), and after it is rejected. If the arm's client treats the duplicate as a fresh grant with a new lifetime, that is a client-side belief the contract does not constrain. A stated outcome: the hook is out of the contract's reach, not the checks'. |

**Consequences for scoring, stated now.** For the first two classes, X3-7's part (ii) (the steward names the decision and failure from the trace) is the only route; part (i) is expected "no" in both arms and is not a difference between arms. A Grok planter choosing one of these classes therefore tests the steward's reading, not the layer. This is registered as a known gap of the observability layer: **a storage-side cross-record ledger check (C1.2 over storage's own order) is absent**; it is not added before X3, because adding it now changes the oracle all four authors receive after the briefs were written. It is a candidate for the next schema version.
